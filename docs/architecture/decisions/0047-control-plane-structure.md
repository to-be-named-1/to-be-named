## Context

**A leader-centered control plane with invariants in the database** (D47). Holding queues, fair share and lease renewals in the leader's memory ([D43](0043-scheduling-and-capacity.md)) requires every agent call to reach the leader. Spreading agent traffic over symmetric replicas would turn renewals into database writes, and routing every write through the leader would make it the bottleneck for every human action. Correctness does not rest on leadership being exclusive: row locks, conditional updates and unique constraints enforce the invariants, and a leader epoch with a wait of one transaction timeout stops a deposed leader's writes, so an overlap of leaders costs fairness only.

**Postgres as the only stateful dependency** (D47). Redis, Kafka and RabbitMQ were considered. The leader's memory already holds the hot state a cache would hold, and it is recovered from Postgres at takeover in the same way, so at the scale targets of [D43](0043-scheduling-and-capacity.md) a cache would add a component without removing work. A broker cannot take part in a Postgres transaction: the outbox would remain behind a relay, and handlers that now complete their row in the same transaction as their effects, one key at a time, would have to tolerate duplicate and reordered deliveries. Postgres alone keeps the control plane simple to build, test and run. Seams for an event relay, a change feed and a rate limiter keep a broker or cache possible; a broker behind the relay, taking event fan-out and retries off Postgres, is the step held for when load tests show the outbox tables to be the limit.

**A pure planner, run once per run** (D47). Placing nodes once, after inputs are resolved, keeps placement deterministic within a run, which plan pinning ([D28](0028-warehouse-connection-policy-and-plan-pinning.md)) relies on; re-planning at each control-flow point was rejected. Planning everything up front is impossible for maps over value outputs, so the run driver instantiates the plan's unit templates as the run proceeds.

**Expected reuse rather than a binding plan** (D47). Between planning and the creation of a unit deep in a run, a cached output may expire or be flagged, or a new one may appear, and keys that depend on value outputs or content hashes exist only at run time. Binding reuse at plan time would pin storage for runs waiting to reach their units and would still need a second lookup.

## Decision

How the control plane is organized: where its components run, how leadership is held and fenced, its bounded contexts and aggregates, the transactions that span them, what each component is responsible for, how the planner works, how runs advance and how the reconciler finds work.

- **Topology.** One active leader runs the agent gateway, the scheduler, the dispatcher and the advancement of runs that follows agent reports. Every other component runs on every replica and claims its work from Postgres: the API, planning, reconciler loops, triggers, outbox handlers, watching the deploy branch and collection marking. Agent calls reach the leader as set out under routing to roles; forwarding agent calls to the leader remains possible. Pinning each agent to a replica by consistent hashing would spread renewals across replicas while keeping them in memory, but admission and advancement would still need one decider, since fair share is global per capacity domain and advancement's counters are held in memory, fed with capacity and outcome reports from every replica; each replica would need its own fencing, and the loss of a replica or a change of membership would need agents to be reassigned. It remains possible if agent traffic outgrows one leader. Holding queues and lease renewals in memory ([D43](0043-scheduling-and-capacity.md)) requires every agent call to reach the leader.
- **Deployment roles.** The control-plane binary may be deployed in roles: `api` (ConnectRPC for the web application and the CLI, serving the single-page application, and refusing agent calls as retryable), `worker` (planning, reconciler loops, outbox and work-row handlers, watching the deploy branch and collection marking), `leader` (eligible for leader election; when elected, it runs the agent gateway, the scheduler, the dispatcher and run advancement) and `all`, the default, which runs everything, so that a single-machine installation runs one process. A process may combine roles. In-process wake-ups remain an optimization within a process; between processes, wake-ups are NOTIFY hints with polling as the guarantee ([D48](0048-execution-mechanics.md)). Roles scale user traffic, planning, reconciliation and event delivery; they do not scale the leader, whose state is held in memory ([D43](0043-scheduling-and-capacity.md)), and beyond it the route remains cells. In the architecture model the server is one container whose components carry a `roles` property, and the deployment views show instances by role.
- **Routing to roles.** Which processes run the `api` role is fixed at deployment, so API traffic reaches them by membership: on Kubernetes a Service selects the pods whose template carries the `api` role, and a pod replaced after a failure comes back from the same template with the same roles; elsewhere only `api` processes are registered with the load balancer. Which process is leader changes at every failover, so agent traffic reaches it by detection. The leader opens the agent port only while it holds leadership, which lets a load balancer that checks only TCP find it. On Kubernetes, whose readiness covers a whole pod, the leader labels its own pod and an agent Service selects that label, which needs permission to patch its own pod; behind other load balancers, a health check on the agent endpoint that only the leader passes routes agents to it. In every deployment, an agent call that reaches a process that is not leader fails, refused at the connection or answered with a retryable error, and the agent retries, so retries remain the fallback. A process reports readiness for the role that receives traffic through it, so a stuck background loop does not take a healthy API out of rotation; its liveness combines a check for each of its roles and fails when any of them stops making progress, so a half-working process is restarted rather than left running.
- **Leadership.** The leader holds a session-level advisory lock on a dedicated connection made directly to Postgres, not through a transaction-pooling proxy; the lock is released when that session ends, in every deployment. Each takeover increments an epoch row. Every leader-only transaction — admission, write leases, declaring an attempt lost, creating a retry — checks the epoch, and a new leader makes no leader-only write until `transaction_timeout` and a margin have passed, so the transactions of a deposed leader have finished or been ended before it acts.
- **Invariants in the database.** Correctness never depends on leadership being exclusive. Row locks, conditional updates and unique constraints enforce the invariants below, so an overlap of two leaders costs fairness, not correctness.
- **Bounded contexts.** Eight: **identity and tenancy** (tenants, principals, memberships and clearance, teams, service accounts, role bindings, projects, tenant resources and their grants, audit); **authoring** (definitions, drafts, platform-held versions, git synchronization, deployments, environment bindings and the compiler); **plugin registry** (format types, implementations, node types, allowed implementations, images); **catalog** (datasets, versions, partition versions, manifests, schemas, positions, frontiers, read records, the cache index, projection state and collection marks); **planning** (the planner, which owns no tables); **orchestration** (triggers, materialization requests, backfills, runs and their plans, task runs and their attempts, map groups, the run driver and the reconciler); **dispatch** (agent pools, capacity domains, agents and enrollment, queues, admission, fair share, leases, write leases and the agent gateway); and **provenance** (a read model over the catalog and orchestration: lineage, tiers, verification and comparator verdicts). Each context has its own Postgres schema and Go package tree, and the outbox and the leader epoch, which belong to no context, sit in a shared schema; other contexts use its Go interface and never read its tables, and import rules are checked in CI by depguard in golangci-lint. A transaction crosses contexts only in the cases named below.
- **Aggregates and invariants.** The dataset head: a single producer ([D13](0013-partitioning-intervals-and-dataset-ownership.md)), dense increasing version numbers, one current version, and no quarantined version current unless released ([D31](0031-execution-state-model.md)). Partition versions: immutable and closed only by the commit transaction under the head lock ([D42](0042-catalog-persistence.md)). The run: resolved inputs and plan immutable once recorded, outcome set once. The task run with its attempts: at most one live attempt, enforced by a partial unique index, dense attempt numbers, and commits only from the current attempt ([D48](0048-execution-mechanics.md)). The write lease: one holder per partition, enforced by a unique index, with dataset-wide leases checked by the epoch-fenced scheduler. The scheduled run: one per workflow, trigger and logical interval, enforced by a unique constraint, so a repeated firing is harmless.
- **Transactions across aggregates.** Three by design: the data commit, including publication groups ([D42](0042-catalog-persistence.md)); the batch from one agent message ([D43](0043-scheduling-and-capacity.md)); and run start, which records the run, its plan and its first task runs. Locks are taken in one order: the epoch check, which takes no lock; task-run rows in ascending identifier order; write-lease rows; dataset head rows in ascending identifier order; then the outbox insert. The consistent order prevents deadlocks and serializes a late commit against the retry that supersedes it.
- **Compiler.** In authoring, on any replica, for each version of a definition: it parses and migrates the IR ([D41](0041-ir-text-form-round-trip-and-structure.md)), pins node-type and workflow versions, inlines `uses` nodes and flattens composites ([D31](0031-execution-state-model.md), [D33](0033-automatic-fusion.md)), type-checks ports and CEL expressions with a static cost estimate ([D41](0041-ir-text-form-round-trip-and-structure.md), [D44](0044-minimum-technology-stack.md)), checks that control flow is structured ([D2](0002-graph-model.md), [D46](0046-control-flow-constructs.md)), expands column selectors and derives output schemas, checks intervals against partitioning ([D13](0013-partitioning-intervals-and-dataset-ownership.md)), checks the single producer at deployment, computes each node's semantic fingerprint ([D8](0008-cache-keying.md)) and hoists invariant nodes. Compiled workflows are stored by semantic hash. It never reads data or catalog versions and never decides placement.
- **Hoisting.** A node inside a map or loop frame that depends on neither the map item, the loop index nor carried state is moved out of the frame and runs once. Its output is then read by several units and must be stored, and the plan shows the move. Deduplicating identical keys when task runs are created was rejected, since task runs would have to wait on each other.
- **Planner.** A pure function in its own context, run on any replica once per run after input resolution; its caller supplies every input. Its passes run in order, without iteration: bind environment names to resources granted to the project and check access under the run's project identity ([D41](0041-ir-text-form-round-trip-and-structure.md), [D45](0045-isolation-enforcement-and-role-model.md)); place each node by the precedence of [D25](0025-processing-engines-and-runtimes.md) — explicit override, hard constraints (empty until [D26](0026-placement-constraints.md)), dialect capability and connection policy ([D28](0028-warehouse-connection-policy-and-plan-pinning.md)), then data location; estimate each node's slice and output ([D34](0034-capacity-and-size.md)); insert repartition steps where a slice fails the capacity check and the node declares a grouping key ([D25](0025-processing-engines-and-runtimes.md), CORE 2.26); fuse by legality and then policy, the ceiling acting as a guard that only splits, forming units and their segments ([D32](0032-execution-unit-structure.md), [D33](0033-automatic-fusion.md)); size each unit, setting its request from declared resources (CORE 2.4) and the estimated working set and checking it against the per-unit ceiling, which is the capacity check of [D34](0034-capacity-and-size.md), and flag units that still exceed it; assign each unit to a pool and so to a capacity domain ([D40](0040-protocol-between-the-control-and-data-planes.md), [D43](0043-scheduling-and-capacity.md)); compute input-addressed keys where their ingredients are known and show expected reuse ([D8](0008-cache-keying.md)); and compare with a pinned plan ([D28](0028-warehouse-connection-policy-and-plan-pinning.md)), recording reasons and the version of every pass. Repartitioning is decided per node before fusion and fusion can only split, so no pass revisits an earlier one. Placement never changes during a run. Re-planning at each control-flow point was rejected because it makes placement non-deterministic within a run and breaks plan pinning; planning everything at run start cannot handle maps over value outputs.
- **Estimation.** Answers the follow-up of [D34](0034-capacity-and-size.md). A unit's input slice is sized from its manifests, including uncompressed sizes recorded from Parquet footers, with an expansion factor per type for the in-memory form. Sizes are propagated through the unit's nodes from the per-node statistics of earlier runs (CORE 6.6), otherwise from conservative defaults, otherwise marked unknown. The memory class decides what the estimate constrains: a small fixed amount for streaming nodes, a moderate memory request and ephemeral disk for spill for spilling nodes, and memory that must hold the state for non-spilling nodes. Estimates are calibrated from measured peak memory and spill (CORE 4.2), kept per unit composition and applied at a high percentile with a margin. CPU is compressible and comes from declared resources or an engine default; GPU is declared. Declared resources act as a floor. With nothing known, the declared or default request is used and the estimate is marked unknown, neither flagged nor refused.
- **Ceilings, quotas and weights.** The effective per-unit ceiling is the lower of the value a tenant Admin declares on the pool and the maximum its agents report ([D34](0034-capacity-and-size.md), [D40](0040-protocol-between-the-control-and-data-planes.md)). Tenant Admins set project quotas (CORE 7.5) and fair-share weights ([D43](0043-scheduling-and-capacity.md)); a Maintainer may set lower limits within the project, such as per-workflow concurrency (CORE 2.2). Authors set only the resources their nodes declare and the parallelism of their maps and backfills.
- **Input resolution.** Resolving means only choosing the versions and positions a run reads. For each internal dataset input, the run driver, through the catalog and in one repeatable-read transaction ([D42](0042-catalog-persistence.md)), applies the node's partition dependency function to the run's interval ([D13](0013-partitioning-intervals-and-dataset-ownership.md)), chooses the version — pinned, coherent along lineage, or current ([D14](0014-input-version-resolution.md)), excluding quarantined versions unless released and using the last valid version where the readiness policy proceeds ([D16](0016-input-readiness-and-degraded-outputs.md)) — and records the partition versions valid at it as identifiers; external sources are resolved by source probes ([D49](0049-source-probes.md)). Other acts are named separately: environment names are bound ([D41](0041-ir-text-form-round-trip-and-structure.md)), node-type and workflow versions pinned, attempts specified by building their unit specification ([D40](0040-protocol-between-the-control-and-data-planes.md)), expressions evaluated, and secrets resolved by the agent.
- **Run driver.** In orchestration; on the leader for advancement after agent reports, and on any replica for commands, through conditional updates. It resolves the run's inputs; creates task runs from the plan's unit templates as the run reaches them — branches taken, map windows over value outputs ([D41](0041-ir-text-form-round-trip-and-structure.md), [D43](0043-scheduling-and-capacity.md)), unrolled iterations with their carried state ([D46](0046-control-flow-constructs.md)) and partitions discovered at run time ([D13](0013-partitioning-intervals-and-dataset-ownership.md)); evaluates conditions and run rules; propagates skips; resolves merges; applies loop termination; makes the authoritative cache lookup; marks task runs ready; decides retries by failure class ([D31](0031-execution-state-model.md)); suspends and resumes for approvals and gate holds; drains on pause; on cancel ends pending work and asks the dispatcher to signal running attempts; and ends the run. It never orders work, talks to agents or performs a commit.
- **Advancement.** A successor's readiness is updated in the transaction that records the upstream outcome, by decrementing its count of pending upstream task runs under its row lock; skips propagate with their reason and merge nodes join ([D46](0046-control-flow-constructs.md)). Large fan-in and run end never update one row per item: map-group counters and each run's outstanding count are held in the leader's memory, written in batches and recounted at takeover. Every action triggered by an event has a level-triggered sweep behind it, which finds runs whose task runs have all ended, completed map groups, attempts offered but never claimed, and expired holds.
- **Run outcome.** A run fails if any of its task runs failed, unless the failure was consumed by a node whose run rule fires on failure ([D41](0041-ir-text-form-round-trip-and-structure.md)); the exact rule is settled with the IR specification. Failing on any failure, and deciding by leaf nodes, were rejected.
- **Cache lookups.** The planner computes input-addressed keys from everything known at run start, including probed external versions ([D49](0049-source-probes.md)), and shows **expected reuse**, binding nothing. The lookup the run driver makes when it creates each task run is authoritative: it completes the key from this run's value outputs and committed content hashes and queries the cache index through the eligibility filter ([D9](0009-cache-scope.md), [D26](0026-placement-constraints.md)), a query in the control plane that involves no agent. A hit records the outcome reused with a reference to the task run reused ([D31](0031-execution-state-model.md)) and protects the reused artifact for the rest of the run. A difference from expected reuse is not a pinned-plan difference. Binding reuse at plan time was rejected: it would pin storage for runs waiting to reach their units, and keys known only at run time would still need a second lookup.
- **Reconciler.** Orchestration's level-triggered loops: schedules and triggers, creating runs idempotently (CORE 3.1, CORE 3.2); runs waiting for inputs ([D16](0016-input-readiness-and-degraded-outputs.md)); materialization requests ([D24](0024-dataset-materialization-requests.md)); backfills, their coalescing ([D20](0020-backfill-commits-and-scheduling.md)) and the final commit of a restatement ([D48](0048-execution-mechanics.md)); and the backstop sweeps. Each target has a work row with its next check time, claimed on any replica with `FOR UPDATE SKIP LOCKED`; events bring the next check forward, and a periodic resync covers anything missed. Watching the deploy branch, collection marking, projection scheduling and probe scheduling use the same work-row mechanism in their own contexts. Purely event-driven handlers were rejected, since one lost or poisoned event would stall a dataset silently.
- **Scheduler and dispatcher.** In dispatch, on the leader only. The scheduler orders and admits ready work: queues per capacity domain, fair share, quotas, write leases and preemption ([D43](0043-scheduling-and-capacity.md)); it never chooses a pool or decides a retry. The dispatcher handles agents and attempts: enrollment and key identity ([D40](0040-protocol-between-the-control-and-data-planes.md), [D44](0044-minimum-technology-stack.md)), capability reports and protocol negotiation, attempt creation and the unit specification, offers, claims and leases ([D48](0048-execution-mechanics.md)), cancellation and preemption signals, state-bearing messages, and commit requests, for which it checks the fencing token and write leases and calls the catalog's commit in the same transaction. It also offers maintenance tasks and probes ([D49](0049-source-probes.md)).
- **Clocks.** Durable timestamps and due times come from the database clock; lease timing uses the leader's monotonic clock.
- **One stateful dependency.** Postgres is the control plane's only stateful dependency. Hot state is held in the leader's memory and rebuilt from Postgres, and telemetry is kept outside it ([D21](0021-architecture-planes.md)). A cache or message broker was considered and not adopted, for simplicity: the leader's memory meets the scale targets of [D43](0043-scheduling-and-capacity.md), and a broker would put a relay in front of the outbox and make every handler tolerate duplicate and reordered deliveries. Three seams are kept, each implemented in-process first: an event relay, so that producers only ever write the outbox; a change feed for live interface updates; and a rate limiter for per-tenant limits on a hosted control plane. A hosted control plane scales by cells, each with its own database and a set of tenants (see the design agenda).
- **Amends.** [D8](0008-cache-keying.md): the plan shows expected reuse, and the lookup at task-run creation is authoritative. [D21](0021-architecture-planes.md): the control plane's components gain the planner and the run driver, and Postgres is its only stateful dependency. [D27](0027-ibis-for-relational-node-definitions.md): the spike also checks spilling forms of pivots and ordered aggregates. [D31](0031-execution-state-model.md): the run outcome rule. [D34](0034-capacity-and-size.md): the estimation method and the effective ceiling. [D43](0043-scheduling-and-capacity.md): the leader election mechanism and epoch, and fair-share weights set by the tenant Admin. [D45](0045-isolation-enforcement-and-role-model.md): tenant Admins set quotas, weights and ceilings, and Maintainers set lower limits.
- **Reuse across modes.** Amended by [D50](0050-development-mode.md): reuse works between development and production in both directions within a project; cache-index entries record the producing run's mode and pool, and a Maintainer may restrict production to outputs of deployed runs or of named pools.

## Follow-ups

- Load testing of the leader-centered topology against the targets of [D43](0043-scheduling-and-capacity.md); putting a broker or cache behind the event-relay, change-feed or rate-limiter seams only if load tests miss those targets through churn in queue tables, if interface fan-out outgrows notification hints, or if hosted rate limiting needs exact shared counters; cells for a hosted control plane (design agenda); the exact run outcome rule and how a fused unit's request combines the needs of its segments, with the IR specification (design agenda); catching up scheduled intervals missed while the control plane was down.
