## Context

[D40](0040-protocol-between-the-control-and-data-planes.md) fixed the shape of the protocol between agents and the control plane: pull-based agents, leases owned by the pool, adoption by any replica, guaranteed state-bearing messages and best-effort telemetry. [D43](0043-scheduling-and-capacity.md) set its timings, [D44](0044-minimum-technology-stack.md) its transport and [D52](0052-agent-identity-by-message-signatures.md) its proofs of identity; [D48](0048-execution-mechanics.md) settled renewals in memory, offers, claims and the stop set. What remained open was the protocol itself: what holds a key and how keys rotate, what a replica's session is, how offers and adoption are spread across replicas, how each message is numbered and answered, where commits survive an outage, how every kind of unit reports its results, how errors are carried, and how the packages are versioned.

Organizations that operate sensitive data environments rotate keys several times a day, so rotation has to be automatic. Replicas of one pool are interchangeable by design and authorization works per tenant and pool ([D43](0043-scheduling-and-capacity.md), [D45](0045-isolation-enforcement-and-role-model.md)), so a key per replica adds no authority; what it adds, once keys are short-lived and held only in memory, is that a stolen key expires on its own and its reuse can be detected.

## Decision

How agents identify themselves and rotate their keys, how a replica's session works, how work is offered, claimed, renewed, adopted, reported and committed, how errors are carried, and how the protocol's packages are versioned.

- **Two tiers of keys.** An enrollment registers a long-lived Ed25519 **enrollment key** for a pool, which may hold several enrollments; the replicas started from one enrollment share its key file. The enrollment key is used only to register replicas. Each replica, one running agent process, generates a **replica key** in memory at start-up, never written to disk, registers it with a request signed by the enrollment key and proving possession of the replica key, and signs all further traffic with it. A replica is identified by a random identifier chosen at start-up and never persisted; it labels the replica's long-poll, heartbeats and logs and grants no authority, since claims, fencing and stop sets work per attempt and task run.
- **Enrollment.** A tenant Admin issues a one-time enrollment token for a pool, with an expiry of 24 hours by default. The token is an identifier and a secret, and the secret never travels: `agent enroll` signs its request with HTTP Message Signatures using `hmac-sha256` keyed by the secret, covering the new public key, and the control plane signs its response the same way, covering its own key, so that a network that inspects TLS can neither enroll in the agent's place nor substitute the control plane's key. The command writes a key file holding the enrollment key, the enrollment's identifier and the pinned key of the control plane; replicas mount it, as a Secret on Kubernetes or a file elsewhere. `agent run` given a token runs the same two steps in one command where no key file exists. An agent never writes a Secret through a backend's API.
- **Replica-key rotation.** A replica rotates its key automatically, every hour by default and configurably down to minutes; the rotation is signed by the current key and proves possession of the new one, the previous key stays valid for one heartbeat for requests in flight, and a key that is not rotated within its lifetime expires. A request signed with a key that has been rotated out marks its enrollment compromised and raises an alert, so a stolen replica key either dies at the next rotation or, if the thief rotates first, is exposed by the real replica's next request.
- **Enrollment-key rotation.** An enrollment key is rotated by enrolling again with a new token, which automation can request through the API under a service account, and by retiring the old enrollment once its replicas have restarted on the new key file. A key that may be stolen never authorizes its own replacement. Running units are backend containers that outlive the agent's process, so restarting replicas loses no work. No maximum key age is enforced; the age and the last use of every enrollment are shown.
- **Revocation.** Revoking an enrollment is either a **retirement**, after which its signatures are refused and its attempts carry on where other replicas adopt them, or a **compromise**, which also ends every attempt the enrollment claimed or renewed, with the outcome lost, the reason recorded, its staged files discarded and the platform retry budget applied ([D31](0031-execution-state-model.md)). Every claim, renewal and commit records the enrollment and replica that sent it, for audit and for compromise handling; committed data is not rolled back automatically. A single replica key can be revoked on its own.
- **The control plane's keys.** The control plane holds one root key, read from its configuration as a secret and pinned by agents at enrollment, and signs responses with short-lived signing keys, each delegated by a statement signed with the root key, every 24 hours by default and configurably down to hourly; an agent accepts a previous signing key until its delegation expires. The root key is rotated on demand by a statement that the previous root key signs; at session start the control plane returns the chain of such statements from the agent's pinned key, and the agent verifies it, holding the result in memory, so the key file is never rewritten. A compromised root key is revoked, which breaks the chain, and every agent enrolls again.
- **Sessions.** A replica's registration is its session. Replica keys and their rotation lineage are kept in Postgres, so sessions survive a failover; capabilities and liveness are held in the leader's memory and rebuilt from the next calls. At registration the replica sends the protocol majors it supports and a list of named features, and the control plane chooses the highest common major or refuses with the range it supports; work that needs a feature is offered only to replicas that declare it. The replica also sends its static capabilities: backend type, region, processor architectures, capacity ceilings, features, its build and the address at which it serves units; a change to any of them is a new session. A registration whose backend or region contradicts the pool's declaration is refused with the reason. A graceful shutdown retires the replica's key and ends its long-poll; a crashed replica's key expires with its lifetime.
- **Freshness.** Every request's signature covers a nonce issued by the leader and a counter. The leader issues a new nonce every heartbeat interval, timed by its own monotonic clock, and every response carries the current one; a request is accepted only with the current or the previous nonce, so a delayed delivery is refused after one to two intervals, and a duplicate within that window is refused by a sliding window of counters kept per nonce. A refused request receives the current nonce and is signed again; after a failover the new leader's nonces make every earlier one stale. Freshness is checked before the status of the signing key, and a public key already known can never be registered or rotated to again, so a replayed registration or rotation is harmless.
- **Message classes.** Amends [D40](0040-protocol-between-the-control-and-data-planes.md). Heartbeats form a class of their own: one per replica, renewing every lease it holds, protected by freshness rather than by sequence numbers, and never retried. State-bearing messages are claims, the transition to running, checkpoint commits, commit requests and end-of-attempt reports; each call carries messages of one kind, batched across attempts, as one method per kind with its own permission check.
- **Offers.** The leader offers each attempt to one replica, round robin among the live replicas that declare the features it needs, and offers it to the next replica if it is not claimed within the offer timeout, one heartbeat interval by default. An offer carries the attempt, its tenant, its session if any and the features it needs. The long-poll returns as soon as anything is pending for its replica, carrying everything pending up to a size limit, and otherwise returns empty after 30 seconds by default, below the idle timeouts of common load balancers and proxies; a second long-poll from the same replica replaces the first. The long-poll carries a closed set of items: offers, stops with their reason (canceled, preempted, fenced or lost), drains, and the log requests of [D65](0065-unit-specification-and-agent-unit-contract.md). They are best effort and not persisted: the stop set in heartbeat responses remains the guarantee, and a drain is restated there until it is acknowledged. Deleting the files that collection marks as unreferenced, and checking managed files against their manifests for changes made out of band, are offered work, done by the maintenance unit's storage deletion and integrity check, which reports differences in its results for the control plane to flag the affected versions, so that agents hold no logic specific to a kind of storage, as for probes ([D49](0049-source-probes.md)) and projection ([D44](0044-minimum-technology-stack.md)).
- **Claims.** A claim call may carry several attempts, each with its own sequence number and its own verdict: claimed, with the launch part of the unit specification and the lease duration relative to receipt; taken, by another replica after a re-offer; or withdrawn, because the attempt was canceled or preempted. The lease starts when the claim is received. A replica that adopts or restarts fetches an attempt's specification with one call, authorized by its pool. Compiled plans travel by content hash and are fetched once through a call of their own, checked against their hash and cached by the agent; large manifests travel by location ([D42](0042-catalog-persistence.md)); everything else is inline.
- **Heartbeats and owners.** A heartbeat lists the leases its replica renews and, from the replica the leader designates as its pool's reporter, the pool's free capacity and backlog, since capacity is a property of the backend that every replica of the pool drives; it acknowledges drains and adoptions. Its response carries the stop set with a reason for each attempt, the attempts adopted and released, the drain state, which replica reports capacity, the lease duration and the current nonce. Each attempt has one owner replica, set by its claim; the owner sends its messages, submits its commits, refreshes its credentials and answers its lease checks. When a replica misses three heartbeats, the leader reassigns its attempts round robin to live replicas, before their leases expire; the adopter finds each unit by its backend label, fetches its specification and renews it, and a unit no longer found ends failed with the infrastructure class. A released attempt is forgotten without stopping its container, since another replica now owns that container. After a failover, owners are rebuilt from the first heartbeats, and an attempt that no replica lists by the end of the grace period is reassigned. Zones are not a placement attribute: a pool is one backend, and a backend spanning zones places containers itself.
- **Timings.** Each timing stays configurable, and a process refuses to start unless the gone threshold is shorter than the lease, the lease covers several heartbeats, the nonce interval equals the heartbeat interval and the grace period is at least one lease.
- **Sequence numbers and answers.** The leader accepts an attempt's state-bearing messages only from its current owner, answering any other replica that it is not the owner, and numbering continues across adoption: each adopted attempt carries the last number applied. An attempt's messages are sequential by nature, so the agent sends its next message only once the previous one is answered, and the leader keeps on the attempt's row, in the same transaction, the last number, a digest of that message and its answer: a duplicate of the last message receives the recorded answer, an older number is answered as already applied, and the same number with a different digest is refused as a conflict. The commit requests of an attempt's independent commit units are parallel by nature, travel together and are answered, when repeated, from their own commit records ([D42](0042-catalog-persistence.md)). A refused transition is answered with the attempt's current state.
- **Commits.** A commit request covers one commit unit: one dataset, one publication group or one append to an open partition, and so one commit transaction ([D42](0042-catalog-persistence.md)). Its identifier is derived from the attempt and the commit unit, so a rebuilt request is the same request, and it carries for each output the dataset and partitions written, the manifest, the row count and the schema, which the control plane checks against the schema derivation produced, with the quality-gate results and the read records of the unit's inputs. A commit call batches requests for transport, each in its own transaction with its own verdict: committed; fenced; quarantined, for a failed gate; awaiting approval, after which the attempt ends held and the control plane completes the commit later ([D48](0048-execution-mechanics.md)); or refused, with its reason. An attempt ends committed when all its commit units are committed, fenced when any is fenced, held when any awaits approval, and otherwise failed with the task-error class. A checkpoint commit has the same shape, with an identifier derived from the attempt and a checkpoint counter; the latest one wins and only it is kept.
- **Durable commits.** Amends [D40](0040-protocol-between-the-control-and-data-planes.md). A unit writes each commit request beside the staged files it commits, on the same storage target, before handing it to its agent, and may then exit; the agent holds the request in memory and submits it, across outages, until it is answered. When an attempt's container has ended without its results acknowledged, the leader offers the maintenance unit's commit recovery, which submits the staged requests through its agent ([D65](0065-unit-specification-and-agent-unit-contract.md)). No agent needs a volume shared between replicas. The hard limit stops running containers and never discards pending commits; whether a late commit still counts is decided by fencing.
- **End reports and results.** An end report carries the outcome; the failure class, with a structured error code and a short message passed through the classification filter, full traces staying in the customer's logs; the exit status; peak memory and CPU time; the durations the agent measured; and the unit's results, in one typed field whose variant depends on the kind of unit: value outputs and row counts, probe results, derivation results, adoption scans, or the results of the maintenance unit's jobs. Results are applied in the end report's transaction, fenced like any state-bearing message, inline up to 1 MiB by default and otherwise by location in the attempt's staging, with a digest. The unit's own failure class prevails; the agent assigns timeout when it stops a unit that exceeded its specification's timeout; the leader assigns lost and fenced, and canceled as soon as it cancels. A unit that ends without its results acknowledged is completed by commit recovery from what it staged, or, where it staged nothing, classed resource exhausted when killed for memory and infrastructure otherwise, since the runtime reports every exception of node code as a task error ([D65](0065-unit-specification-and-agent-unit-contract.md)).
- **Errors.** A call fails as a whole only when nothing in it can be processed; everything specific to one message is a typed verdict in a successful response. A process that is not the leader answers `unavailable`, and the agent retries with exponential back-off and jitter; a rate-limited call is answered `resource_exhausted` with a retry delay; a stale nonce is answered `aborted` with the current nonce, and the agent signs the request again at once; a bad signature or unknown key is answered `unauthenticated` without retry, and a replica key that was rotated out or expired registers again with the enrollment key, never retrying the old key; a revoked enrollment is answered `permission_denied`, and the replica exits, leaving its units to revocation; a registration outside the version window or contradicting its pool is answered `failed_precondition`, and the replica exits; a malformed call is answered `invalid_argument`. State-bearing messages are retried until answered, with full jitter from 0.5 to 30 seconds by default and no retry limit; the long-poll reopens at once after a normal return. Overload is answered like rate limiting, and admission ([D43](0043-scheduling-and-capacity.md)) bounds the work offered.
- **Packages.** The protocol's packages are named under a placeholder prefix, `tobenamed`, replaced when the product is named, since package names travel in the paths of calls and the types of error details; the agent protocol is `tobenamed.agent.v1alpha1`. Its methods are split into two services by the key that signs them: enrollment and replica registration, and everything else, signed by the replica key. Amends [D44](0044-minimum-technology-stack.md): a package with an unstable suffix, `v1alpha1` or similar, makes no compatibility promise, and negotiation accepts only an identical version; `buf breaking`, at WIRE_JSON with unstable packages ignored, gates every stable package, which follows the version window. The control plane serves the current stable major and the previous one, the previous for at least 12 months after its successor ships; changes within a major are additive, with features gating new behavior; on a major change the control plane is upgraded first, and the web application shows the agents on a major due to be dropped. Go code is generated with connect-go v2, its generators pinned as Go tool dependencies, and committed under `internal/gen/` at the root; a protobuf check runs `buf lint`, `buf breaking` against the pull request's base and the generation again, failing on any difference, in a pinned container and only where `proto/` changed.
- **Amends.** [D23](0023-artifact-storage-layout.md): staging also holds the commit requests a unit hands to its agent. [D40](0040-protocol-between-the-control-and-data-planes.md): enrollment and replica keys; heartbeats form their own class; durable commits are kept in staging, and the agent's buffer is in memory. [D42](0042-catalog-persistence.md): unreferenced files are deleted, and integrity checks run, as jobs of the maintenance unit. [D43](0043-scheduling-and-capacity.md): a heartbeat is sent per replica. [D44](0044-minimum-technology-stack.md): the long-poll carries offers, stops, drains and log requests, and deleting storage is offered work; `buf breaking` gates stable packages. [D48](0048-execution-mechanics.md): the offer timeout is one heartbeat interval by default. [D52](0052-agent-identity-by-message-signatures.md): enrollment registers an enrollment key, replicas sign with keys of their own, and responses are signed with keys the control plane's root key delegates. [D60](0060-code-layout-and-tooling.md): generated Go code and the protobuf check.

## Consequences

- Rotating keys several times a day needs no person: replica keys rotate on their own, and re-enrollment can be scheduled through the API.
- A stolen replica key expires within its rotation interval, and its reuse is detected.
- The leader keeps a constant amount of state per attempt for sequencing, and replica keys, enrollments and their lineage are the only protocol state it persists beyond attempts and commits.
- Units must stage their commit requests, and attempts whose agent was lost are completed by commit recovery, which adds a small unit per such attempt.
- Generated code for the protocol is committed and generated again in CI, which gains a protobuf check.

## Rejected alternatives

- One key per replica, each replica enrolling with a token of its own: every replacement or scale-up of a replica needs a new token, and authorization never uses a replica's identity.
- One key shared by all the replicas of an enrollment and rotated by them: replicas would need write access to a shared Secret and would have to coordinate, and the old and new keys would overlap for as long as a mounted Secret takes to reach every pod.
- Rotation signed by the key being replaced: a stolen key could rotate itself and push out the real one.
- Trusting the control plane's key on first use over TLS, or a fingerprint of it carried in the token: the first fails where TLS is inspected, and with the second the token crosses that network, so another party could enroll first.
- One generation of the control plane's key, rotated through a chain of statements: frequent rotation would lengthen the chain without bound.
- Renewals as state-bearing messages, one per attempt: up to 50,000 numbered messages every 10 seconds at the ceiling of [D43](0043-scheduling-and-capacity.md), protecting an effect that the next renewal supersedes.
- Offering every attempt to every replica: every replica races for every attempt.
- Self-directed adoption by surviving replicas: replicas would need to know each other's liveness and would race for the same units.
- Ownership epochs restarting numbering at each adoption: a counter more than continued numbering under an owner check needs.
- A volume shared by every replica for durable commits: many clusters lack storage that every pod can mount, and it is one more component to operate.
- Units waiting for their commit's answer: a unit holds its resources through an outage and is stopped at the hard limit.
- A separate method for each kind of unit's results: several paths, each with its own fencing and duplicate handling.
- Timestamps in signatures for freshness: they rely on the agent's clock ([D44](0044-minimum-technology-stack.md)).
- Packages named `v0`: buf's standard lint rule requires versions numbered from 1.
