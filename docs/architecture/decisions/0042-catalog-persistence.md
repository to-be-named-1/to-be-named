## Context

**Snapshots and recorded identifiers rather than cutoffs** (D42). A sequence number or timestamp is assigned before its transaction commits, so a later commit can become visible before an earlier-stamped one; any cutoff by such a value is safe only below a watermark. Run inputs are therefore resolved from a database snapshot and recorded as version identifiers, and only as-of-time queries use a cutoff, below an approximate watermark that can later be made exact.

The reasoning on ConnectRPC rather than REST and on projection on by default, in [D44](0044-minimum-technology-stack.md), on row-level security for the tenant only, in [D45](0045-isolation-enforcement-and-role-model.md), on one outbox row per handler, in [D48](0048-execution-mechanics.md), and on sandboxes as lines rather than copies, in [D50](0050-development-mode.md), also cites this decision.

## Decision

How the catalog stores datasets, versions, partitions, manifests, files, schemas and read positions in Postgres, what a data commit writes, and how datasets on object storage are made readable by external engines.

- **Partitions by validity interval.** Each partition version records the dataset version from which it is valid and, once replaced, the version at which it stopped being valid. A commit writes only the partitions it changed and closes the rows they replace; reading a dataset as of version S selects the partition versions valid at S, which serves pinning ([D14](0014-input-version-resolution.md)), as-of reads ([D38](0038-point-in-time-retrieval.md)) and restatements ([D20](0020-backfill-commits-and-scheduling.md)). An append to an open partition creates a new partition version whose segments are the previous segments, by reference, plus the new one, and marking it complete is a further version, so partition versions stay immutable ([D15](0015-atomic-publication.md)). A publication group commits several datasets in one transaction.
- **Ordering and visibility.** Commits to the same dataset take turns under a lock on its head row, so version numbers and commit timestamps follow true commit order within the dataset; commits to different datasets run in parallel and finish in any order. A run resolves all its inputs inside one repeatable-read transaction and records the resolved version identifiers, so no ordering value decides what it sees ([D14](0014-input-version-resolution.md)). Commit timestamps serve as-of-time queries ([D38](0038-point-in-time-retrieval.md)), answered only for times older than a watermark. In the first slice the watermark is approximate: commit transactions run under a short `transaction_timeout`, as-of queries are answered only for times older than a settling window comfortably longer than that timeout and any clock skew on failover, and a commit whose timestamp has aged beyond half the window before committing rolls back and retries with a fresh one. The watermark sits behind an interface, so an exact watermark derived from the commits still in flight can replace it without changing stored data. No global sequence is kept: a sequence number or timestamp is assigned before its transaction commits, so neither may decide visibility except below a watermark.
- **Positions and read records.** Positions are one tagged type with a kind per change-detection strategy ([D37](0037-incremental-extraction-state.md)): ordered ranges of timestamps, keys or log offsets with stated inclusivity; opaque tokens, ordered by commit; and file sets, held inline when small and externally when large. A read of an internal dataset records the range of versions consumed ([D12](0012-streaming-readiness.md), Seam 5), which is also the cursor of an incremental transform. A read record is kept per task run per input. The cursor frontier is keyed by the source declaration and the consuming node, not by a raw dataset, which may not exist when the read is ephemeral ([D35](0035-ephemeral-extraction.md)).
- **Commit transaction.** A data commit is one database transaction containing the fencing check, the manifests and partition versions, the version row, the read records, the frontier update, the move of the head pointer and an outbox row. Everything that follows from a commit — staleness marks downstream, the degraded cascade ([D16](0016-input-readiness-and-degraded-outputs.md)), notifications, reconciler wake-ups and external projections — is derived afterwards from the outbox by idempotent consumers, keeping the commit path minimal. A replayed commit request receives the original answer.
- **Control-plane boundary.** The control plane holds no storage credentials ([D40](0040-protocol-between-the-control-and-data-planes.md)), so everything it needs — resolution, unit specifications, capacity statistics ([D34](0034-capacity-and-size.md)), preview metadata and collection decisions — is in Postgres. Manifests are held inline by default; above a configurable file count the listing is written to customer storage as a manifest file read only by agents and units, while Postgres keeps the file count, bytes, rows and a digest of the listing. Garbage collection runs in two phases: the control plane marks unreferenced artifacts and an agent maintenance job deletes the files with its own credentials and confirms; where a dataset is projected, the Iceberg snapshots that reference the files are expired first ([D44](0044-minimum-technology-stack.md)). Integrity checks for out-of-band modification ([CORE 6.24]({workspace}/documentation#3)) run as data-plane jobs.
- **Identifiers.** Artifact identifiers are time-ordered UUIDs generated in the data plane, so units write to staging without a control-plane round trip, including during a control-plane outage ([D21](0021-architecture-planes.md), [D23](0023-artifact-storage-layout.md)). The tenant leads every primary key ([D30](0030-tenancy-and-isolation-enforcement.md)); amended by [D45](0045-isolation-enforcement-and-role-model.md), every unique constraint and foreign key also includes it. Dataset version numbers are integers per dataset, assigned under the head lock. Large append-heavy tables — task runs, attempts, read records — are designed to be partitionable by time, so archiving remains possible ([S5]({workspace}/documentation#7.5)).
- **States and history.** A version is declared, materializing, available, superseded or expired, or quarantined and then possibly released ([D31](0031-execution-state-model.md)); it carries a degraded flag ([D16](0016-input-readiness-and-degraded-outputs.md)) and, where applicable, a backfill identifier ([D20](0020-backfill-commits-and-scheduling.md)). Deleting expired bytes never deletes version, read, position or frontier records; runs decay to Traceable rather than losing their history ([D7](0007-reproducibility-guarantee.md), [D37](0037-incremental-extraction-state.md)).
- **Schemas.** Each distinct schema is stored once, in Arrow logical types ([D41](0041-ir-text-form-round-trip-and-structure.md)), keyed by its hash, and each version references its schema; contract evolution is checked at publication.
- **External readability.** A managed dataset stored on object storage is a set of identity-addressed files in the customer's storage ([D23](0023-artifact-storage-layout.md)), and which of them form the current version is known only to the catalog; an external engine pointed at the files would read superseded and quarantined data. After each commit, a data-plane job driven by the outbox therefore writes Iceberg metadata pointing at the files of the current version and registers it in the customer's Iceberg catalog, so external engines read a consistent, slightly delayed view, without copying data and without a second commit point. Making Iceberg the physical format, with two commit points to reconcile, was rejected. The projection is part of the first slice ([D29](0029-first-development-slice.md)). Datasets whose storage target is a warehouse or lakehouse table, and external datasets, are read natively by the customer's tools and need no projection. Amended by [D44](0044-minimum-technology-stack.md): the projection is a maintenance unit using PyIceberg that replays every version that became current as its own snapshot, into REST or SQL catalogs; datasets are stored as Parquet with partition keys as columns; and projection is on by default wherever a catalog is configured, with restricted datasets held back unless their owner allows them.
- **Amends.** [D14](0014-input-version-resolution.md): inputs are resolved inside one repeatable-read transaction and recorded as version identifiers. [D23](0023-artifact-storage-layout.md): a snapshot selects partition versions by validity interval rather than listing them.
- **Outbox rows.** Amended by [D48](0048-execution-mechanics.md): a commit writes one outbox row for each handler subscribed to its event rather than one row per event, each claimed, retried and dead-lettered on its own; handlers that need order process by dataset version, never by outbox identifier.
- **Lines.** Amended by [D50](0050-development-mode.md): heads, versions and partition versions belong to a line, production or a sandbox; version numbers are kept per dataset and line, a sandbox version records its parent or fork point, and every unique constraint and foreign key on these tables includes the line.

## Follow-ups
