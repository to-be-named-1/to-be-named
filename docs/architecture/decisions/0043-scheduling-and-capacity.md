## Context

**The platform as the queue** (D43). Delegating ordering to the backend was rejected: backends see the platform as one consumer, know nothing of its classes, leases or projects, differ between deployments and, when over-submitted, hide queued work. Fair share uses dominant resources rather than attempt counts because fused units differ in size by orders of magnitude, and its cost grows with active consumers, not task runs. [D20](0020-backfill-commits-and-scheduling.md)'s promise that backfills never delay current pipelines was weakened because, without preemption, a running backfill attempt can delay later production work; preemption is available per pool.

**Single-tenant pools and capacity domains** (D43, amended). Pools that several tenants share would put every tenant's credentials, secrets and egress filtering into one agent, a permanent exposure paid for a fully managed topology the first slice does not include. Keeping pools bound to one tenant and grouping pools that share capacity into a domain gives fairness between tenants and correct admission, and the seams kept make shared pools cheap to add if they are ever needed.

As first recorded, this decision computed fair share per pool and expected a pool to serve several tenants in the fully managed topology, contradicting [D30](0030-tenancy-and-isolation-enforcement.md) and [D40](0040-protocol-between-the-control-and-data-planes.md), which bind each pool to one tenant. Capacity domains resolve the contradiction.

The reasoning on a leader-centered control plane with invariants in the database, in [D47](0047-control-plane-structure.md), and on write leases held by the task run, in [D48](0048-execution-mechanics.md), also cites this decision.

## Decision

How the control plane queues, orders and admits work, the scale it is designed for, and the timings of the protocol between the planes. The priority classes and the backfill guarantee are agreed provisionally, to be revisited with operating experience.

- **Scale targets.** Targets to be confirmed by load testing, with a ceiling the design must not preclude: task runs per run, 10,000 in the first slice and 1,000,000 at the ceiling; attempts running at once per control plane, 2,000 and 50,000; sustained state transitions, 500 and 10,000 per second; tenants per control plane, one when self-hosted and thousands when hosted. Scheduling overhead — from a task run being ready and admissible to being claimed — has a 95th-percentile target under two seconds. Queue wait, from ready to admissible, and start latency, from claimed to running, are reported but not targeted, since they depend on load, policy and the backend ([CORE 4.3]({workspace}/documentation#3)).
- **The platform is the queue.** Work is admitted to a pool only up to what the pool can start promptly, judged from the free capacity and the backlog of submitted but unstarted units its agents report ([D40](0040-protocol-between-the-control-and-data-planes.md)) and bounded by the capacity ceilings ([D34](0034-capacity-and-size.md)); admission backs off when starts lag. Where pools share a capacity domain, admission is judged against the capacity of the domain, counted once. The backend scheduler decides only which node runs each container, because work queued inside the backend loses the platform's ordering and visibility, and a cluster shared with the customer's own workloads offers less than its configured capacity. Backend-native queueing, such as Kueue on Kubernetes, may later be evaluated for admission on such pools.
- **Fair share.** Computed per capacity domain, over dominant resources — CPU, memory and GPU — weighted and hierarchical (tenant → project → workflow), on exponentially decayed usage with a configurable half-life, using one priority queue per capacity domain and a limited scan depth; its cost grows with the number of consumers with ready work, not with task runs. Agent pools are bound to one tenant ([D30](0030-tenancy-and-isolation-enforcement.md), [D40](0040-protocol-between-the-control-and-data-planes.md)), so the tenant level takes effect where pools of several tenants share a capacity domain, as in the fully managed topologies; in hybrid and self-hosted deployments fair share operates across projects and workflows. GPU is a dimension from the start ([MLE 2.2]({workspace}/documentation#6)); fractional and time-sliced sharing is left to the backend. Hard quotas ([CORE 7.5]({workspace}/documentation#3)) are ceilings separate from fair share. A pool may map projects to backend namespaces, queues or accounts, so that the backend's own policy and accounting also apply; the platform never relies on the backend for ordering. A hosted control plane separately limits each tenant's use of its own work — admission decisions, state transitions, API requests and metadata storage — in every topology.
- **Priority classes.** Interactive — development sample runs and canvas previews ([CORE 6.6]({workspace}/documentation#3), [DS 1.4]({workspace}/documentation#5)), with a small reserved slice of capacity; production — scheduled runs, manual runs against production and materialization requests ([D24](0024-dataset-materialization-requests.md)); backfill ([D20](0020-backfill-commits-and-scheduling.md)); and optional best effort. Fair share orders work within a class; queued work gains priority as it waits, and an optional minimum share per class can be configured, so lower classes do not starve.
- **Backfill guarantee.** Backfills are admitted only to idle capacity, production work never queues behind waiting backfill work, and running backfill attempts are not stopped by default; production work may therefore wait for a running backfill attempt to finish. A pool may enable preemption of lower-class attempts once production work has waited beyond a threshold; attempts are disposable ([D21](0021-architecture-planes.md)), checkpoints limit lost work ([D31](0031-execution-state-model.md)) and side-effecting steps are guarded by their lease check ([D40](0040-protocol-between-the-control-and-data-planes.md)). Amends [D20](0020-backfill-commits-and-scheduling.md).
- **Exclusion while running.** At admission the scheduler takes a write lease on every partition a unit will write, and a unit whose partitions are held waits in the queue; the lease is released when the attempt commits or ends. The commit lock of [D42](0042-catalog-persistence.md) orders commits only, and alone would let two concurrent writers of a partition both commit. The same lease implements the per-workflow overlap policy ([CORE 3.7]({workspace}/documentation#3)) and the queueing of extraction runs on a cursor-based source ([D37](0037-incremental-extraction-state.md)).
- **Queue entry.** Only ready work is queued; runs waiting for inputs ([D16](0016-input-readiness-and-degraded-outputs.md)), approvals or gate holds ([D31](0031-execution-state-model.md)) hold no capacity, and a retry rejoins the queue in its original class after its back-off.
- **Maps.** A map is tracked by a map-group record with counters for total, pending, running, succeeded and failed items. Its task runs are created in windows sized to the map's parallelism, and cache lookups for its items are batched the same way, so large maps neither flood the queue nor enlarge the fair-share computation; every task run still exists in the end, for provenance. This settles the question [D31](0031-execution-state-model.md) deferred. State transitions are written in batches, one transaction per agent message, to tables partitionable by time ([D42](0042-catalog-persistence.md)).
- **High availability.** A single active scheduler holds queue and fair-share state in memory; Postgres remains the source of truth, accumulated usage is persisted or derived from attempts so that a failover does not reset fair share, and a standby takes over through leader election. To the rest of the system a failover is a control-plane restart, to which the grace period of [D40](0040-protocol-between-the-control-and-data-planes.md) applies.
- **Timings.** Defaults, all configurable: a heartbeat every 10 seconds per agent, renewing all its leases; a lease of 60 seconds, tolerating about five missed heartbeats; a grace period of 60 seconds, at least one lease, after a control-plane restart; a hard limit of 10 minutes for stale attempts ([D40](0040-protocol-between-the-control-and-data-planes.md)); cancel latency up to one heartbeat interval, reduced by [D44](0044-minimum-technology-stack.md) to about one round trip while the agent's long-poll is open.
- **Capacity domains.** Pools that share physical capacity, such as several pools on one Kubernetes cluster, form one capacity domain; a pool alone on its backend is a domain of its own. Without domains, every pool on a shared backend would report the same free capacity and admission would count it more than once. Pools remain bound to one tenant.
- **Seams for shared pools.** Pools serving several tenants, which a fully managed topology with many small tenants might want to reduce agent overhead and sign-up latency, are not built. They stay cheap to add: every agent message carries its attempt's tenant ([D40](0040-protocol-between-the-control-and-data-planes.md)), agent internals are keyed by tenant, and the agent-facing authorization check asks whether the agent may act for the attempt's tenant ([D45](0045-isolation-enforcement-and-role-model.md)). Only the vendor would operate such agents, so no customer upgrade would be involved.
- **Amends.** [D20](0020-backfill-commits-and-scheduling.md): backfills are admitted only to idle capacity and may be preempted per pool. [D31](0031-execution-state-model.md): the task runs of a map are created in windows sized to its parallelism. [D40](0040-protocol-between-the-control-and-data-planes.md): agent messages carry the attempt's tenant and agent internals are keyed by tenant. [D45](0045-isolation-enforcement-and-role-model.md): the agent-facing check is phrased per attempt.
- **Leadership.** Settled by [D47](0047-control-plane-structure.md): the leader holds a session-level advisory lock, and every leader-only write checks an epoch incremented at takeover. Fair-share weights are set by the tenant Admin ([D45](0045-isolation-enforcement-and-role-model.md)).
- **Write leases.** Amended by [D48](0048-execution-mechanics.md): a write lease is held by the task run while it is active, including retry back-off, and released when it ends or suspends; a unit whose output partitions are discovered at run time takes a lease on the whole dataset. By default runs of a workflow may overlap, serialized per partition by these leases; preventing or queueing overlap is set per workflow ([CORE 3.7]({workspace}/documentation#3)).
- **Development runs.** Amended by [D50](0050-development-mode.md): only sample runs started from the canvas, including sessions, are interactive; sample runs started by CI or the API and full-scale development runs use the best-effort class, which is therefore always present, unless a Maintainer raises them to production. Development work forms its own node in fair share under each project, with one child per principal.

## Follow-ups

- Load testing of the scale targets; revisiting the priority classes and the backfill guarantee with operating experience; evaluating backend-native queueing such as Kueue; the default half-life of decayed usage; how pools are assigned to capacity domains, by declaration or from the backend identity agents report; pools serving several tenants in the fully managed topology, only if per-tenant agent overhead or sign-up latency proves material; whether a run waiting for its inputs counts as in flight when a workflow's overlap policy is to queue ([CORE 3.7]({workspace}/documentation#3)).
