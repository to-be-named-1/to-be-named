## Context

Most installations begin with data that already exists: tables in a warehouse or a lakehouse catalog, and folders of files laid out by path convention, often without a table format. The decisions so far assume that a managed dataset begins empty. [D4](0004-datasets-as-first-class-objects.md) says that bulk data is connected or registered in place, but does not define registering in place. [D13](0013-partitioning-intervals-and-dataset-ownership.md) allows a single producer per dataset and gives no path from an existing pipeline to the platform. The bootstrap of [D37](0037-incremental-extraction-state.md) is always a full load, with no way to continue from the existing pipeline's last position. The integrity rule of [D4](0004-datasets-as-first-class-objects.md) assumes that the platform owns the prefix in which a dataset's files sit.

Storage targets are defined for Iceberg and Delta tables and for warehouse tables ([D4](0004-datasets-as-first-class-objects.md), [D15](0015-atomic-publication.md)). Hive-style tables, folders of Parquet or ORC files with partition directories registered in a metastore without a table format, and Hudi tables can be read but are not defined as targets, and the platform's identity-addressed paths ([D23](0023-artifact-storage-layout.md)) cannot be browsed by dataset.

Under [D36](0036-data-engineering-practice-first-reproducibility-by-choice.md), adoption must not require copying or rewriting existing data, and must not force a single switchover. The ways existing data comes under the platform reduce to five cases, separated by who keeps producing the data and by what the existing data is: a table with its own commit mechanism, files without one, or data the customer wants to leave behind. [D4](0004-datasets-as-first-class-objects.md)'s line between managed and external datasets and [D13](0013-partitioning-intervals-and-dataset-ownership.md)'s single producer hold in every case.

The Iceberg specification requires writers to write every column to data files, and requires readers to take an identity partition value from the manifest when the column is missing from a file, for metadata-only migrations of Hive tables. PyIceberg's `add_files`, which registers existing Parquet files without rewriting them, takes partition values only from column statistics, and registers a file whose partition key exists only in its path with a null partition value.

The status is Partial: the modes and their mechanisms are decided, while the comparisons that validate a new workflow before switchover and the detection of another producer's writes to a warehouse table are open.

## Decision

Existing data comes under the platform in one of five modes, chosen per dataset. Nothing is copied unless copying is chosen explicitly, and a dataset passes from an existing producer to the platform by one explicit act of its owner.

- **Terms.** The **platform-managed prefix** is the storage the platform owns: a prefix inside customer storage, or vendor or bundled storage ([D4](0004-datasets-as-first-class-objects.md)). **Customer-managed tables and folders** are everything else in the customer's storage.
- **Start fresh.** Mode 1: there is no existing data, and the first platform run produces version 1, in the platform-managed prefix or a target table.
- **Reference.** Mode 2: the existing producer keeps writing and the dataset stays external. The platform reads it in place and records its versions as read ([D4](0004-datasets-as-first-class-objects.md), [D49](0049-source-probes.md)). Every adoption may begin in this mode.
- **Take over a table in place.** Mode 3: an existing Iceberg, Delta, Hive-style or warehouse table becomes the dataset's storage target ([D4](0004-datasets-as-first-class-objects.md), [D15](0015-atomic-publication.md)). The baseline is the table's current state or snapshot; the platform writes through the table's own commit, and existing readers keep reading the same table.
- **Own manifest over existing files.** Mode 4: existing files without a table format, tabular or not, become a managed dataset without being copied. The baseline is a manifest over the files where they are, and new versions are written to the platform-managed prefix.
- **Copy.** Mode 5: the existing data is copied into the platform-managed prefix as the baseline, to reorganize it, change its format or leave the old storage behind. Copying is an explicit choice, never a default ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)).
- **Path-pattern partition mapping.** In modes 2, 4 and 5, the dataset's owner maps existing folders to the dataset's partitions ([D13](0013-partitioning-intervals-and-dataset-ownership.md)) with a path template relative to the dataset's root, made of time fields (`%Y`, `%m`, `%d`, `%H`) and named keys (`{region}`), such as `date=%Y-%m-%d/` or `{region}/%Y/%m/%d/`. Hive-style `key=value` segments are recognized without being declared. A partitioned external dataset is read partition by partition, a mode 4 baseline builds its partition versions from the mapping, and a copy resumes partition by partition.
- **Time zone and granularity.** The template states the time zone of its folder dates, which must equal the dataset's partition time zone; a mismatch rejects the mapping ([D13](0013-partitioning-intervals-and-dataset-ownership.md)). The template's finest time field must equal the dataset's partition granularity; a finer template is rejected.
- **Layout check.** A probe lists the dataset's root, and every file must match the template or an ignore list, such as `_SUCCESS`, `*.crc` or temporary files. Any other file rejects the mapping, and the offending paths are shown.
- **Newest partition.** At adoption every mapped partition counts as complete except the newest, which the owner confirms as complete or keeps open, since the existing producer may have been writing to it when it stopped ([D13](0013-partitioning-intervals-and-dataset-ownership.md)).
- **Baseline.** Modes 3, 4 and 5 begin with a baseline: version 1 of the dataset, with the producer recorded as "adoption", as an upload records the upload ([D4](0004-datasets-as-first-class-objects.md)); the schema in observed mode (DE 5.8); and the partitions from the mapping, or from the table's own metadata in mode 3. History before adoption is not imported, and lineage begins at the baseline.
- **Files outside the prefix.** In mode 4, adopted files are referenced read-only and are never deleted unless the owner hands their retention over to the platform ([D4](0004-datasets-as-first-class-objects.md)). Restating an adopted partition writes new files under the platform-managed prefix. At adoption each file's size, ETag and modification time are recorded, so that out-of-band changes are detected without reading every byte; full digests are an optional, explicit scan.
- **Tables taken over in place.** A table taken over in mode 3 is a storage target ([D15](0015-atomic-publication.md)) and is never projected; the projection still never takes over a table it did not create ([D44](0044-minimum-technology-stack.md)). Every platform commit to an Iceberg or Delta table carries the dataset and version as commit properties; a snapshot without them is flagged, and the platform stops committing to the table, as [D44](0044-minimum-technology-stack.md) provides for projected tables.
- **Hive-style tables.** A Hive-style table can be a storage target. New files are written to a fresh directory and the partition's location is then repointed in the metastore, which switches one partition atomically; a version that changes several partitions is reported as partially published ([D15](0015-atomic-publication.md)).
- **Hudi tables.** Hudi tables are read in modes 2 and 4 and are not a storage target.
- **Readable prefix.** A dataset's artifacts are written under `artifacts/<tenant>/<project>/<path.name>--<short-id>/<partition>/<artifact-id>/…` ([D23](0023-artifact-storage-layout.md)). The dataset segment joins the dataset's path and name with a shortened form of its identifier, so that it stays unique when a name is reused after deletion and still ties a dataset's files together if renames are introduced ([D19](0019-stable-dataset-identity.md)). The partition segment holds one `key=value` level per partition key, in declared order, with values escaped as in Hive-style paths, and is omitted for an unpartitioned dataset. Artifacts that belong to no dataset, such as cached intermediates and previews, keep `artifacts/<tenant>/<project>/<artifact-id>/…`. Storage can be browsed by dataset and partition, files stay immutable and shareable between versions, and which files are current is still known only from the manifest.
- **Observation.** In mode 2, the owner may turn on observation of an external dataset; it is off by default. A probe records each new version it sees, as a snapshot identifier, an object version or a changed file listing, without reading the data, and the dataset stays external. Observation gives a history of versions to validate against before switchover; it costs probes, so it is never imposed ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)).
- **Switchover.** Moving a dataset from mode 2 to mode 3, 4 or 5 is one explicit act of its owner, after which the new node is the dataset's single producer ([D13](0013-partitioning-intervals-and-dataset-ownership.md)). The existing producer must be stopped first; a later write by it is flagged by the detection of mode 3 or by the integrity check of [D4](0004-datasets-as-first-class-objects.md). Before switchover, the new workflow is validated in development mode ([D50](0050-development-mode.md)) against the external dataset's observed versions.
- **Incremental loads.** At adoption the owner may set the starting position, as a watermark, an offset or a set of files, recorded as the baseline's position, so that the first platform run continues from it ([D37](0037-incremental-extraction-state.md)). Without one, the full-load bootstrap of [D37](0037-incremental-extraction-state.md) applies.
- **Schedules.** Intervals before adoption count as complete, and the schedule begins at the next interval; earlier intervals are filled or restated by ordinary backfills ([D20](0020-backfill-commits-and-scheduling.md)).
- **Probes.** Adoption adds three kinds of probe, run in the data plane because the control plane holds no credentials ([D40](0040-protocol-between-the-control-and-data-planes.md)): the layout check; the baseline scan, which lists existing files with their sizes, ETags and modification times or reads a table's current state; and the observation of an external producer ([D49](0049-source-probes.md)).
- **Keys only in the path.** Adopted files whose partition key exists only in their path are not projected, and the reason is shown. Restating such a partition writes the key as a column, after which it is projected. This is the only exception to [D44](0044-minimum-technology-stack.md)'s rule that every partition key is stored as a column, and it applies to adopted files only.
- **Scope.** Converting pipeline definitions from other tools is out of scope; existing code runs unchanged in units ([D32](0032-execution-unit-structure.md)).
- **Amends.** [D4](0004-datasets-as-first-class-objects.md): registering in place is defined by modes 3 and 4; a managed dataset may reference files outside the platform-managed prefix, read-only, with size, ETag and modification time recorded in place of checksums and deleted only if their retention is handed to the platform; Hive-style tables are storage targets. [D13](0013-partitioning-intervals-and-dataset-ownership.md): existing folders are mapped to partitions by a path template whose time zone and granularity equal the dataset's; adopted partitions are complete except the newest, which the owner confirms; switchover is the act by which a node becomes an adopted dataset's single producer. [D15](0015-atomic-publication.md): a Hive-style table commits each partition by repointing its location in the metastore, and a version spanning several partitions is partially published; platform commits to tables taken over in place carry the dataset and version, and other snapshots are flagged. [D23](0023-artifact-storage-layout.md): a dataset's artifact paths include a segment of its path, name and short identifier, and its partition values; a manifest may reference adopted files outside the prefix. [D37](0037-incremental-extraction-state.md): the starting position may be set at adoption and recorded as the baseline's position. [D44](0044-minimum-technology-stack.md): adopted files whose partition key exists only in their path are not projected, as the one exception to keys stored as columns; tables taken over in place are not projected. [D49](0049-source-probes.md): probes gain the layout check, the baseline scan and the observation of an external producer.

## Rejected alternatives

- Recording adoption only as amendments to [D4](0004-datasets-as-first-class-objects.md), [D13](0013-partitioning-intervals-and-dataset-ownership.md) and [D37](0037-incremental-extraction-state.md), under which the flow from existing data to a managed dataset would be recorded nowhere as a whole.
- Moving adopted files under the platform-managed prefix, which is a copy and a delete on object storage, expensive and not atomic ([D23](0023-artifact-storage-layout.md)).
- Writing in the customer's own path layout, which overwrites or moves files when versions change and breaks immutability and atomic publication ([D15](0015-atomic-publication.md), [D23](0023-artifact-storage-layout.md)).
- Leaving Hive-style tables without a storage target, which would force their readers to move to the projection.
- A dataset segment of the name alone, which after a rename would leave files under a name that no longer identifies the dataset, and after a name is reused would mix a new dataset's files with a deleted one's.
- A dataset segment of the identifier alone, which cannot be read.
- Recognizing only Hive-style `key=value` segments, which misses folders laid out by date alone, such as `2026/10/13/`.
- Skipping files that do not match the template with a warning, which can silently drop data.
- Rolling folders finer than the partition granularity up into coarser partitions, which adds complexity for little gain.
- Rewriting adopted files to add a partition key that exists only in their path, which is a copy, available as mode 5.

## Follow-ups

- Which comparisons validate a new workflow against an external dataset's observed versions before switchover, such as row counts, keys and column profiles.
- How a write by another producer to a warehouse table taken over in place is detected.
- Projecting adopted files whose partition key exists only in their path with explicit partition values, once a writer path that supports it is verified (iceberg-go, the fallback of [D44](0044-minimum-technology-stack.md), or writing manifests directly), with a case for such files in [D44](0044-minimum-technology-stack.md)'s interoperability suite.
- Hudi tables as a storage target, once their writer libraries pass the conformance suite ([D18](0018-format-types-plugin-implementations-and-bindings.md)).
