## Context

**Sandboxes as lines rather than copies** (D50). Copying datasets per developer, as development schemas do, costs storage and compute and goes stale; publishing to production would break [D45](0045-isolation-enforcement-and-role-model.md). Because partitions are selected by validity interval ([D42](0042-catalog-persistence.md)), a sandbox line can share every partition it has not written with production by reference, so isolation costs only what a change rewrites.

**Reuse across modes by key** (D50). A full-scale development run and the production run of the same interval on the same input versions compute outputs with the same keys, so recomputing after deployment would repeat work already held; chiefly a restatement checked in a sandbox is served from it once deployed. Teams that require production data to be computed on production infrastructure can restrict this.

**Referential subsetting for samples** (D50). Independent random samples lose most matches in every join, and hash sampling on one key fails as soon as inputs join on different keys, as facts joined to several dimensions do. Sampling a driving input and keeping the matching rows of every input joined to it keeps joins meaningful on a sample.

**Sessions with a fresh process per unit** (D50). A container start for every run from the canvas dominates the wait in the builder's main loop. A persistent kernel would let one run's state change the next run's result; a warm container that starts a fresh process per unit saves the start and keeps caches keyed by identity without carrying state.

**Side effects never fall back to production** (D50). Reads may fall back to production bindings so that development needs no duplicated connections, but a side effect executes only through a binding written for a non-production environment, so a development run can never reach a production system by accident.

**Development reads bounded by clearance** (D50). Development runs execute code that may not have been reviewed. Limiting a person's development run to data that person is cleared to read means such code can expose nothing its author could not already see, while production runs keep the project identity of [D45](0045-isolation-enforcement-and-role-model.md).

**Development as its own share** (D50). Running development work in the production class could delay scheduled pipelines, and running automated runs in the interactive class would crowd out people at the canvas; a best-effort class and a development node in fair share keep each in its place.

## Decision

How work is developed and tried before it is deployed: the kinds of development run, where their outputs go, how sandboxes work, how development and production reuse each other's results, how inputs are sampled, how runs from the canvas are made fast, and how bindings, side effects, governance, scheduling, provenance and retention apply.

- **Kinds.** Two kinds of development run: a **sample run**, on a sample of its inputs, and a **full-scale development run**, on full inputs for one logical interval or a range, reading exactly the partitions a production run of that interval would read. A **preview** is a canvas action that starts a sample run of the node being edited, on demand, with an optional automatic refresh after edits.
- **What may run.** A draft, recorded as a snapshot of its IR with its base commit ([D45](0045-isolation-enforcement-and-role-model.md)); a committed version that is not deployed, such as a branch head, so that CI and reviewers can run it; or a deployed version run in development mode. Scheduled work, event triggers and materialization requests always use deployed definitions.
- **Selections.** A run may execute a whole workflow or a selection of nodes. At the **selection boundary**, an upstream node changed by the definition, or downstream of a change, is rerun; an unchanged node with a stored output, a published dataset or a retained unit-boundary artifact, is read from the sandbox where it has a version and otherwise from production; an unchanged node whose output was never stored is rerun from the nearest stored output. Whether a node is unchanged is decided by its key ([D8](0008-cache-keying.md), [D47](0047-control-plane-structure.md)). A sample run samples at the boundary.
- **Run record.** Mode, kind, origin (canvas preview, canvas run, CI or API), definition source, selection, sandbox, sample specification, fusion mode and intermediates setting, environment, the clearance that bounded its reads and the side effects it suppressed. Defaults depend on the origin: runs started from the canvas preview maps over their first few items and unrolled loops for their first few iterations, and any sample run may limit a map whose collection does not shrink with the sample.
- **Outputs.** Sample runs write only run-scoped artifacts, so sampled data never mixes with full-scale data. Full-scale development runs commit to a sandbox. Publishing to production was rejected because production heads change only through deployed definitions ([D45](0045-isolation-enforcement-and-role-model.md)), and copying datasets per developer because it costs storage and compute and goes stale.
- **Lines.** Every head, version and partition version belongs to a line: the dataset's production line or a sandbox's line. Version numbers are kept per dataset and line; write leases are keyed by dataset, line and partition, so sandbox and production writers never block each other; each line's head has its own lock ([D42](0042-catalog-persistence.md), [D48](0048-execution-mechanics.md)).
- **Forking and reads.** A sandbox forks a dataset on its first commit to it and records the production version the run had resolved as its fork point. Partitions the sandbox has written come from its line; those it has not written come from production as of the fork point, by reference. A rebase action moves the fork point to the current production version and shows which forked datasets production has moved on. Datasets the sandbox has never written are read from production's current version. Each input of a sandbox run resolves to the sandbox head where one exists, otherwise to the production head ([D14](0014-input-version-resolution.md), [D47](0047-control-plane-structure.md)).
- **Commits and the outbox.** Sandbox commits use the same transaction, fencing and lease check as production ([D48](0048-execution-mechanics.md)). Outbox rows carry the line, and each handler declares the lines it serves: projection, staleness and the degraded cascade for production consumers, reconciler wake-ups, freshness and notifications serve production only; staleness within a sandbox and the comparison with production serve sandbox lines. Sandbox versions are never projected ([D44](0044-minimum-technology-stack.md)).
- **Gates and retention.** A failed gate quarantines a version on the sandbox line only, and the sandbox owner may release or discard it there. Production partitions a sandbox inherits are protected for the sandbox's lifetime, as operational protection bounded by its idle expiry ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)).
- **Scope and lifecycle.** One sandbox per author per branch for runs of drafts; one per branch for runs of committed branch heads, such as CI; one per author in projects without git. A sandbox is created by the first full-scale development run in its scope, can be rebased, reset or discarded, and is removed when its branch is deleted or deployed or after an idle period; artifacts referenced only by its lines are then collected ([D42](0042-catalog-persistence.md)).
- **Visibility and new datasets.** Project members see a sandbox's metadata, and data content needs clearance ([D45](0045-isolation-enforcement-and-role-model.md)); sandboxes appear under the sandbox, never in production views, and are never shared across projects ([S20]({workspace}/documentation#7.20)). A dataset declared only in a draft exists only in the sandbox, with an identity scoped to it, until deployment creates the production dataset. Warehouse and lakehouse targets, which cannot carry an overlay, write to a development schema named by the bindings once pushdown is introduced.
- **Comparison with production.** A full-scale development run reports, for each dataset it wrote, a comparison with production: row counts, schema changes, changed keys and, where a comparator exists, a verdict within tolerance ([D7](0007-reproducibility-guarantee.md), [CORE 5.7]({workspace}/documentation#3)).
- **Reuse.** Development runs reuse production outputs and production reuses the outputs of full-scale development runs, within the project and through the eligibility filter ([D9](0009-cache-scope.md), [D26](0026-placement-constraints.md)). Production reuses a development output for every interval the development run computed on the same input versions, chiefly restatements and backfills of changed logic; the production commit then references the same artifacts and applies production's governed fields. Gate verdicts are reused with the output, since a gate's definition is part of the key; approvals for gated publication are still given in production. Sample outputs never share keys with production, since their inputs are samples. A Maintainer may restrict production to outputs of deployed runs or of named pools, for teams that require production data to be computed on production infrastructure; the restriction is off by default.
- **Sampling.** Applied at the selection boundary. The default is **referential subsetting**: in each group of inputs connected by joins, a driving input, the largest unless the author chooses, is sampled by a seeded hash of its key, and every input joined to it keeps only rows whose join key matches, recursively along the join graph. Inputs below a size threshold are read whole; inputs connected by no join take an independent random fraction; the partition subset is one chosen interval, normally the latest; a row cap bounds the driving input. Any input may instead be bound to a fixture dataset, which CI normally uses ([MLE 6.1]({workspace}/documentation#6)). Samples are built by a sample-building unit and stored as sample artifacts keyed by the input versions and the sample specification, which is part of each sampled input's identity; external sources are sampled at the probed version ([D49](0049-source-probes.md)). The author sees each input's sample size and the share of rows matched in each join. Inspection and preview samples remain with [S3]({workspace}/documentation#7.3).
- **Fusion and intermediates.** A development run chooses its fusion mode, automatic (the policy and the author's splits) or unfused, and how many intermediates to keep: none, statistics and samples, or full. Sample runs default to automatic fusion with full intermediates, full-scale development runs to automatic fusion with statistics and samples ([D33](0033-automatic-fusion.md)). Inspection of nodes inside fused units applies to every run ([CORE 6.6]({workspace}/documentation#3)); development runs differ only in their defaults.
- **Sessions.** Sample runs started from the canvas may run in a **session unit**: a warm container for one author, project, image and pool that executes successive runs, each unit in a fresh process, keeping only what is keyed by identity, such as the pulled image, sample artifacts and compiled plans, so a result never differs from a fresh container's. Each unit is still its own task run and attempt, recording the session it ran in. A session is sized for the largest unit it has served, up to the interactive ceiling, and counts against the interactive class's reserved slice and the project's quota while alive; it ends after an idle time or a maximum lifetime, and a unit too large for it runs as an ordinary unit. If a session dies, its attempt fails with the infrastructure class and is retried ([D31](0031-execution-state-model.md)). The protocol is fixed now: a session lease, offers that name a session, and credentials scoped per attempt ([D40](0040-protocol-between-the-control-and-data-planes.md)); whether a session runs several attempts at once is open. A persistent kernel keeping state between runs was rejected, since results would depend on earlier runs, as were sessions shared by several authors.
- **Bindings and side effects.** A development run uses the bindings of a non-production environment, the development environment by default, recorded on the run. For logical names it does not define, reads fall back to production bindings, and secrets are resolved likewise for those reads ([D40](0040-protocol-between-the-control-and-data-planes.md), [D41](0041-ir-text-form-round-trip-and-structure.md)). A node with external side effects executes only if the chosen environment binds its target itself; otherwise it is suppressed and records its target, operation, row count, schema and a sample of what it would have sent, under the source's classification ([CORE 2.12]({workspace}/documentation#3)). Sandbox artifacts are written to the storage target the chosen environment binds for each dataset, falling back to production's.
- **Reads bounded by clearance.** A development run started by a principal reads nothing classified above that principal's clearance; an input above it stops the run at planning, and cache reuse is limited the same way ([D9](0009-cache-scope.md), [D45](0045-isolation-enforcement-and-role-model.md)). CI service accounts carry their membership's clearance. Production runs keep the project identity of [D45](0045-isolation-enforcement-and-role-model.md).
- **Governed fields.** In development runs, governed fields take their deployed values, except that a draft or undeployed commit may raise protection: a sandbox output's classification is the highest of the deployed declaration, its inheritance along lineage ([DE 5.9]({workspace}/documentation#4)) and any raise in the draft. Datasets declared only in a draft inherit their classification along lineage and start with an observed schema. Bindings and project settings come only from deployed definitions.
- **Contracts, approvals and publication.** Enforced contracts, and contracts changed in the draft, are checked against development outputs; the run reports which consumers a deployment would break and refuses nothing ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)). Development runs cannot approve model versions ([MLE 3.4]({workspace}/documentation#6)), perform gated publication to production or release production quarantines ([D31](0031-execution-state-model.md)); approval nodes are passed through as simulated unless the author chooses to pause at them.
- **Who may start them.** Operators may start development runs of commits and deployed versions; Developers also of their own drafts, which stay private to their author; CI service accounts of commits, within their clearance ([D45](0045-isolation-enforcement-and-role-model.md)). Development runs and their suppressed side effects are audited ([CORE 7.4]({workspace}/documentation#3)).
- **Scheduling.** Sample runs started from the canvas, including sessions, use the interactive class; sample runs started by CI or the API and full-scale development runs use the best-effort class, which is therefore always present, unless a Maintainer raises a project's development runs to the production class ([D43](0043-scheduling-and-capacity.md)). Development work forms its own node in fair share under each project, with one child per principal, whose weights the tenant Admin sets ([D47](0047-control-plane-structure.md)); a Maintainer may cap development concurrency and compute within the project's quota. Best-effort development attempts may be preempted where a pool enables it.
- **Cost.** Development runs are attributed to their triggering principal and project and marked as development ([CORE 4.5]({workspace}/documentation#3)), and jobs on customer backends carry the run's mode in their tags ([CORE 4.8]({workspace}/documentation#3)).
- **Provenance and retention.** Development runs are recorded at every level ([D31](0031-execution-state-model.md)), with tiers computed as for any run ([D7](0007-reproducibility-guarantee.md)); approvals and verification claims cite only production runs, and the reproducibility setting does not extend to them ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)). They are hidden by default from production run history, lineage and version history, and shown in a development view per project and author. Initial defaults, configurable per project and revisited with [S15]({workspace}/documentation#7.15): artifacts of sample runs started from the canvas kept for 24 hours, of other sample runs for 7 days, of full-scale development runs for the life of their sandbox; sandboxes expire after 14 idle days; development run records are kept for 30 days and their audit records for the audit retention. An artifact that production reuses then follows production retention. Development run records are stored in time partitions separate from production's, so that short retention drops partitions ([D48](0048-execution-mechanics.md), [S5]({workspace}/documentation#7.5)).
- **Environments.** A sandbox is not an environment. A staging environment could later be a long-lived, deployed line; how deployment maps to environments remains a follow-up of [D45](0045-isolation-enforcement-and-role-model.md) ([MLE 6.2]({workspace}/documentation#6)).
- **Amends.** [D9](0009-cache-scope.md): the eligibility check applies a development run's principal's clearance. [D31](0031-execution-state-model.md): approval nodes are simulated in development runs, and the run record gains the development fields. [D32](0032-execution-unit-structure.md): a unit may run in a session container, in a fresh process. [D33](0033-automatic-fusion.md): development runs choose their fusion mode and intermediates. [D40](0040-protocol-between-the-control-and-data-planes.md): offers may name a session, sessions hold leases, and credentials are scoped per attempt in a session. [D41](0041-ir-text-form-round-trip-and-structure.md): development runs use non-production bindings, with reads but not side effects falling back to production. [D42](0042-catalog-persistence.md): heads, versions and partition versions belong to a line. [D43](0043-scheduling-and-capacity.md): the best-effort class is always present, development work has its own fair-share node, and only runs from the canvas are interactive. [D44](0044-minimum-technology-stack.md): sandbox versions are never projected. [D45](0045-isolation-enforcement-and-role-model.md): development reads are bounded by clearance, drafts may only raise protection, deployed bindings apply, and who may start development runs. [D47](0047-control-plane-structure.md): reuse works across modes, cache-index entries record mode and pool, and production reuse can be restricted. [D48](0048-execution-mechanics.md): write leases are keyed by line, outbox rows carry the line, and handlers declare their lines.

## Rejected alternatives

- Preview as a kind of its own, since it is a sample run with interactive defaults.
- Development outputs kept only per run, which would stop a change being built up across runs.
- Development datasets copied per developer.
- Publishing development outputs to production.
- Sampling by first rows, independent fractions or one shared hash key alone.
- Running every run from the canvas as an ordinary unit.
- A persistent kernel.
- Side effects falling back to production bindings.
- Development runs reading with the project's permissions regardless of who started them.
- Drafts lowering governed protection.
- The production class for development work by default.
- The interactive class for CI.
