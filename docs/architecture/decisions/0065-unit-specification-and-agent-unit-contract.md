## Context

[D40](0040-protocol-between-the-control-and-data-planes.md) fixed that a unit talks only to its local agent, through a local endpoint, and named the unit specification and the agent–unit contract as contracts versioned on their own; [D61](0061-logging-and-configuration.md) left units no configuration beyond the address of that endpoint and left open how the logs of node code reach the agent; [D50](0050-development-mode.md) fixed that a session receives its units through the contract. [D64](0064-agent-protocol.md) settled the protocol between agents and the control plane, in which each attempt has one owner replica and ownership moves on adoption.

On Kubernetes, units and agent replicas are separate pods, and traffic between pods crosses the cluster network unencrypted unless the cluster's network is configured to encrypt it. Node code runs untrusted in units, so the contract has to show which attempt is calling. Agents are upgraded on customers' schedules, while the images units run are selected by the control plane, so what units execute has to be able to change without an agent upgrade ([D44](0044-minimum-technology-stack.md), [D49](0049-source-probes.md)).

## Decision

How a unit reaches its agent, what it is given, how it obtains credentials and secrets, how it hands over its commits and results and when it may exit, how it checks its lease before a side effect, how its logs and progress are kept and read, how sessions receive their units, and how the Python side is built.

- **The endpoint.** Each replica serves units at an address of its own, which it reports at registration ([D64](0064-agent-protocol.md)), and the owner passes that address to each unit it launches, the one setting a unit reads ([D61](0061-logging-and-configuration.md)). When its owner cannot be reached, a unit makes one locate call through the pool's shared address; the replica that answers asks the leader, which knows every attempt's owner, and returns the owner's address. During a control-plane outage no attempt changes owner, and a unit retries.
- **Which attempt is calling.** Before claiming an attempt, its owner generates a random token and sends its hash in the claim, where it is kept on the attempt; the token reaches the unit in a mounted file, never in an environment variable, and every call presents it. An adopting replica receives the hash with the specification, so the token survives adoption without replicas sharing a key, and it is refused once the attempt has ended. The token is the unit's identity to the agent: it unlocks that attempt's specification, credentials, secrets and commits and nothing else.
- **Encryption of the hop.** The endpoint is served over TLS with a certificate authority per pool, held by the control plane. At registration, the leader issues each replica a short-lived certificate for its address for units, requested with a signature by its replica key and rotated with that key ([D64](0064-agent-protocol.md)). A unit receives its pool's certificate authority at launch, beside its token, and trusts any replica of its pool, including an adopter and the replica that answers a locate call. The same holds on every backend, including a single machine.
- **Two parts of the unit specification.** The **launch** part is read by the agent: the image digest, resources, timeout, credential scopes, secret references, staging prefixes, the session and the token's hash; it belongs to the agent protocol's package. The **execution** part is read only by the unit and travels through the agent as opaque bytes with its type and major version; it is the unit-specification contract of [D40](0040-protocol-between-the-control-and-data-planes.md), in its own package, `tobenamed.unit.v1alpha1`. What units execute therefore changes with the images the control plane selects, never with an agent upgrade.
- **Which major a unit reads.** Each image declares, in a label, the majors of the execution part its runtime reads, and the plugin registry records them with the image. The dispatcher writes the execution part in the highest major the image reads; an image that reads none fails at planning, with that reason. This holds for every image alike.
- **The execution part.** The identity of the attempt: tenant, project, run, task run, attempt and index path. Its inputs: each dataset or source with its resolved version or probed position, its manifest inline or by location with a digest, the reader it is opened through, a dataset-family implementation at its version or a connector with its connection and secret references, and its schema's hash, checked when opened ([D62](0062-source-reads-and-publication.md)). Its segments in order: each segment's kind, which unit inputs or earlier outputs bind to its inputs, and its compiled plan with its value expressions, by hash, or a Python block's entry point and parameters, or a command line. Its outputs: published, with the dataset, partitions, artifact, staging path, commit unit and publication group; passed to a later segment; or values. Its quality gates, the location of the latest checkpoint and the idempotency key of each side-effecting step. It holds no IR, no credentials, no secret values and no telemetry settings. A unit fetches it through the endpoint at start-up, and fetches compiled plans by hash through the same endpoint, from the agent's cache.
- **Credentials.** The agent mints a credential for each attempt and each credential scope, narrowed to the scope's paths by the storage's own mechanism: a session policy on an assumed role, a credential access boundary, or a shared access signature for a directory or prefix. Storage that cannot narrow a credential to a path is not admitted as a storage target, and the agent never falls back to a broader credential; a scope too large for one credential is split into several. A unit asks for a scope's credential with its token and refreshes it at half its lifetime, 15 minutes by default within the issuer's limits; once the attempt ends, nothing more is issued. The runtime passes credentials to the readers and writers it uses and never puts them in process-wide environment variables. An issued credential cannot be recalled, so its lifetime bounds the exposure of a revoked attempt.
- **Secrets.** A unit asks for a secret by reference with its token; the agent resolves only the references in that attempt's launch part, returns the value over the encrypted hop, writes it to no disk or log, and caches values in memory, keyed by tenant and reference, for 5 minutes by default.
- **Handing over results.** Every request that points at staged data is written beside that data before it is handed to the agent, whether a commit request, a checkpoint commit or an append ([D64](0064-agent-protocol.md)). At the end, a unit writes a **completion record** to the attempt's staging location, holding its results, usage, outcome and failure class and the locations of its staged commit requests, then calls `Finish` with the same content; the agent acknowledges it once held, submits the commit requests, collects their verdicts, settles the outcome and sends the end report. A unit exits once `Finish` is acknowledged, or after waiting 5 minutes by default without an acknowledgment, since its completion record is durable. During a run, checkpoint commits and appends are handed over without blocking; the unit keeps each request until its verdict arrives and sends unanswered requests again to a new owner after adoption, and a fenced verdict, like the stop set, stops the unit.
- **Endings without an acknowledged `Finish`.** When an attempt's container ends without an acknowledged `Finish`, its owner reports the ending with the backend's status, and the leader offers the maintenance unit's commit recovery. Commit recovery submits what the attempt staged, its completion record, commit requests and checkpoint commits, in order; where nothing was staged, it reports the attempt failed, resource exhausted when the container was killed for memory and infrastructure otherwise. Agents never read storage to tell these cases apart.
- **Side effects.** Before a side-effecting step, a unit asks its owner, which asks the control plane at that moment whether the attempt is current and not ended, the test that fences commits. A positive answer also records an intent: the task run, the step, its idempotency key, the attempt and the time. The check is therefore state-bearing, and steps run in order. A retried attempt's check returns any earlier attempt's intent for the step, so node code can inspect the target before acting again, and a step performed again after an earlier attempt began it is marked as possibly performed more than once wherever its target lacks idempotency keys; delivery to such targets stays at least once ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)). Where the control plane cannot be reached, the step waits and checks again; an attempt that is not current is stopped. The SDK offers one construct for a side-effecting step, which performs the check, records the intent and gives node code the step's idempotency key and any earlier intent; it is refused in node types that do not declare side effects ([CORE 2.12]({workspace}/documentation#3)) and returns that the step was suppressed or redirected in verification and development runs ([D50](0050-development-mode.md)).
- **Logs.** Settles [D61](0061-logging-and-configuration.md)'s follow-up. The runtime writes its logs and those of node code that use `logging` as JSON to standard error with the attempt's attributes; other output of node code and native libraries goes to standard output and standard error as it is. The backend captures both, and the customer's collectors read them there; container labels carry the attempt. The runtime also writes its log stream to the attempt's staging in numbered chunks, every few seconds and at `Finish`, kept as long as the attempt's records ([S15]({workspace}/documentation#7.15)), so that every installation can read its attempts' logs with or without an observability stack.
- **Reading logs.** Each pool declares whether users' browsers can reach its storage. Where they can, the default, the web application reads an attempt's chunks from customer storage through short-lived pre-signed URLs that the agent signs on request, including the names of chunks still to come, and polls for new chunks while the attempt runs; log content then never passes through the control plane. Where they cannot, an Admin's choice stated for the pool, logs are relayed through the agent and the control plane: from the backend's log stream while the container exists, and through the maintenance unit's log reading afterwards, with rates and sizes limited. Requests for logs are checked against the attempt's project before they are passed to an agent ([D45](0045-isolation-enforcement-and-role-model.md)).
- **Progress.** A unit sends structured progress through the endpoint, the segment, its phase and the rows and bytes so far, never free text; the agent forwards the latest for each attempt every few seconds, best effort, and the leader holds it in memory for the web application. The final figures arrive in the end report.
- **Sessions.** A session is a lease holder like an attempt, without a task run or an outcome: it is offered with its launch part, claimed by its owner, renewed by its owner's heartbeats, adopted when its owner is lost and stopped through the stop set, and the control plane starts and ends it. An attempt that names a session is offered to the session's owner. The session container pulls its attempts from its owner with a session token, issued like an attempt's token, which is good only for that and for the session's own lifecycle and never for credentials or secrets; each attempt comes with its execution part and its own token and runs in a fresh process with a fresh working directory, removed when the process exits, so that it uses the contract exactly as a unit in its own container does. A session declares how many attempts it runs at once, one by default, and several may be assigned to it so that the next is ready. A process that dies ends its attempt as any unit's ending does; a session container that dies ends its attempts the same way, and its lease ends.
- **The Python side.** The client lives in the unit runtime, never in the SDK: where node code needs the endpoint, for side effects or progress, the SDK defines an interface that the runtime implements and the SDK's testing module fakes. The client is connect-py with its own protobuf implementation, `protobuf-py`, and `pyqwest`, pinned exactly in images, since the runtime shares its environment with node code and `google.protobuf`, which authors' code often pins, does not mix across major versions. The Python code for the execution part and the contract is generated with generators pinned in `uv.lock`, committed under `units/src/units/_gen/` and checked by the protobuf check ([D64](0064-agent-protocol.md)). The contract's package is `tobenamed.agentunit.v1alpha1`, served by the agent, with its methods split into two services by the token that authenticates them: one for attempts and one for sessions.
- **Amends.** [D22](0022-deployment-topologies.md): logs are read from customer storage, or relayed where browsers cannot reach it, rather than tailed through the agent. [D23](0023-artifact-storage-layout.md): staging also holds completion records and log chunks. [D40](0040-protocol-between-the-control-and-data-planes.md): the unit specification has a launch part and an execution part; units authenticate with a token per attempt over TLS from a certificate authority per pool; logs are read from customer storage. [D44](0044-minimum-technology-stack.md): connect-py, `protobuf-py` and `pyqwest` on the Python side of the contract. [D47](0047-control-plane-structure.md): the plugin registry records the majors of the execution part each image reads. [D50](0050-development-mode.md): how sessions receive their attempts, and the protocol allows several at once. [D60](0060-code-layout-and-tooling.md): where generated Python code lives. [D61](0061-logging-and-configuration.md): how the output and logs of node code are kept and read.

## Consequences

- A runtime feature reaches every deployment with the images the control plane selects, without an agent upgrade.
- Units hold credentials only for their own attempt and their own paths, for a bounded time.
- Every installation can read its attempts' logs, and where browsers reach storage the control plane never carries their content.
- Clusters must allow units to reach their agent replicas, and buckets read from browsers need CORS for the web application, as uploads already do.
- An attempt in a session uses the same contract as any other, and only its delivery differs.

## Rejected alternatives

- One address for the whole pool, with every replica forwarding calls to the owner: a forwarding hop and authentication between replicas on every call.
- Trusting the network instead of a token per attempt: any container that reaches the endpoint could act for any attempt.
- Plain HTTP on the hop: credentials and secrets in responses would cross the cluster network readable.
- A certificate per replica pinned by the unit: after adoption, a unit could not trust a replica it was never told about.
- An agent replica on every node, reached through a socket on the node: units would mount a host path, which the baseline Pod Security Standard forbids, or a CSI driver the customer must install.
- An agent inside each unit's pod: it would need an identity of its own, or the enrollment key in every pod where node code runs.
- Relying on the cluster's network encryption, a service mesh or a workload-identity system: each is the customer's choice and cannot be assumed.
- One document read by both the agent and the unit: every change to execution would wait for customers' agent upgrades.
- Credentials for the whole pool, trusted to stay within their paths: any unit could touch anything the pool can.
- Units waiting for every verdict before exiting: they would hold their resources through an outage.
- A separate report method for each kind of unit: several paths, each with its own fencing.
- Logs only through the customer's observability stack: an installation without one could not read why an attempt failed.
- Logs always relayed through the control plane: content and load on the control plane even where browsers could read storage directly.
- connect-py with `google.protobuf`, or grpcio: either would collide with versions of `google.protobuf` pinned by authors' code.
