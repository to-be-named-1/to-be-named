## Context

**Row-level security for the tenant only** (D45). Application scoping alone leaves one forgotten predicate between tenants, the risk recorded in [D30](0030-tenancy-and-isolation-enforcement.md). Policies for project permissions were rejected because they would join membership tables for every row and duplicate rules better tested in code; the tenant predicate is cheap because the tenant leads every key ([D42](0042-catalog-persistence.md)). The database therefore guards the hard boundary and the application the finer ones.

**Runs act with the project's permissions** (D45). Using the triggering user's permissions would make the same workflow behave differently depending on who started it, and would break scheduled work when its author left or changed role.

**Clearance separate from roles** (D45). [D9](0009-cache-scope.md) already required a principal to be cleared for an output's classification. Holding clearance on the membership, with a default that covers everything below restricted, lets ordinary work proceed without ceremony while restricted data needs an explicit grant.

**Drafts rather than a commit per save** (D45). Committing every canvas save fills history with unnamed intermediate states and takes the meaning of a commit away from its author. Drafts held by the platform keep git a record of deliberate changes. Workflow publishing was renamed deploying so that publication refers only to datasets.

**Git owns history; the platform owns deployment** (D45). Version control of the platform's own was rejected: engineers would lose pull-request review, continuous integration and ordinary code history, and the platform would be rebuilding a commodity. Making the platform authoritative with git as a mirror lets git and the platform drift apart when an imported change is refused. Accepting whatever is merged would let anyone with merge rights change governed settings, so deployment is an act of the platform, which checks governed fields however a change arrives.

As first recorded, this decision accepted changes merged in git under their git author. Deployment is now an act of the platform, and governed fields are checked however a change arrives.

The reasoning on one outbox row per handler, in [D48](0048-execution-mechanics.md), and on sandboxes as lines rather than copies and development reads bounded by clearance, in [D50](0050-development-mode.md), also cites this decision.

## Decision

How the isolation required by [D30](0030-tenancy-and-isolation-enforcement.md) is enforced, who may do what, whose permissions runs execute with, and how workflow edits reach git. Completes [D30](0030-tenancy-and-isolation-enforcement.md).

- **Mechanism.** Postgres row-level security enforces the tenant, the hard boundary of [D9](0009-cache-scope.md). Project scope, roles and visibility are enforced by a mandatory authorization layer in the control plane. Encoding project permissions in policies would join membership tables for every row; a project-level backstop in the database, from the caller's readable projects, can be added later.
- **Database roles.** An owner role runs migrations only; the application role is subject to row-level security; a system role with `BYPASSRLS` serves only the components listed under system scope. Every table has row-level security enabled and forced, since table owners otherwise bypass it.
- **Failing closed.** Each transaction sets the tenant with a transaction-local setting, and policies read it with `current_setting`, cast to the identifier type, so a transaction that has not set it fails with an error rather than seeing every tenant's rows. A table with row-level security and no policy denies everything.
- **Schema rules.** Amends [D42](0042-catalog-persistence.md). Every unique constraint and foreign key includes the tenant, because Postgres checks them outside row-level security and they could otherwise reveal another tenant's rows. Views are created with `security_invoker`, so the caller's policies apply. Partitioned tables are accessed only through their parents, whose policies apply to partitions read that way. `COPY FROM` is unavailable on tables with row-level security, so batched writes ([D43](0043-scheduling-and-capacity.md)) use multi-row `INSERT`; each batch comes from one agent and therefore one tenant. Policies compare the tenant by equality, which is leakproof, so indexes remain usable.
- **System scope.** The system role only finds work across tenants: claiming outbox rows, building scheduler queues and fair-share state ([D43](0043-scheduling-and-capacity.md)), reconciler wake-ups, marking for retention and collection, and metering. Every change to a tenant's records happens in a transaction scoped to that tenant, and only the named components can reach the system connection pool. Platform staff have no standing access to tenant records on a hosted control plane; support access is break-glass: time-limited, audited and visible to the tenant.
- **Data access.** sqlc with pgx v5: queries are written in SQL and compiled to typed Go, and every query runs through one helper that opens a tenant-scoped transaction. CI checks that every table has row-level security enabled and forced with a policy, that every unique constraint and foreign key includes the tenant, and that no query run for one tenant returns data seeded for another.
- **Authorization.** Every API method declares the permission it requires and how its resource is found, as an option on its protobuf definition ([D44](0044-minimum-technology-stack.md)). An interceptor checks the caller's role bindings before the handler runs, and a method without the annotation is refused. Agent-facing methods check the agent's tenant and pool ([D40](0040-protocol-between-the-control-and-data-planes.md)). Amended by [D43](0043-scheduling-and-capacity.md): the check asks whether the agent is authorized for the attempt's tenant, which for an agent bound to one tenant is its own. A resource the caller cannot read is reported as not found rather than forbidden, and lists are filtered in the query ([D30](0030-tenancy-and-isolation-enforcement.md)). Authorization decisions on changes and on data access are audited (CORE 7.4).
- **Principals.** A person has one identity, from the identity provider, and a membership in each tenant they belong to; requests name the tenant they act in. Teams group members, and role bindings may name them. Service accounts are principals for CI and automation (MLE 6.1). Agents are not principals; they keep the key identity of [D40](0040-protocol-between-the-control-and-data-planes.md) and [D44](0044-minimum-technology-stack.md).
- **Roles.** Fixed roles bundle fine-grained permissions such as `workflow.edit`, `run.trigger`, `dataset.read_data`, `dataset.manage`, `quarantine.release` and `members.manage`. At tenant level: **Admin** manages members, teams, service accounts, projects, agent pools and enrollment, storage targets, connections, catalogs and tenant policy; **Member** may receive project roles and create projects unless the tenant disables it; **Auditor** reads the audit trail and all metadata, but no data content. At project level, each role including the one before: **Viewer** sees workflows, runs, lineage and catalog metadata; **Operator** triggers runs, re-runs, backfills and materialization requests, and pauses and cancels them; **Developer** edits workflows and dataset declarations, except their governed fields, and commits them; **Maintainer** manages project settings, including the reproducibility setting ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)) and environment bindings ([D41](0041-ir-text-form-round-trip-and-structure.md)), manages project membership, and deploys by direct commit.
- **Bindings.** A role binding names a principal, a role and a scope: the tenant, a project, or a single resource such as a workflow (CORE 7.1). Bindings only grant; there are no deny rules, so a principal's permissions are the union of its bindings. Making something less visible than its project means placing it in another project. Custom roles and attribute-based policy can be added later behind the policy extension interface ([D5](0005-distribution-and-tenancy.md)).
- **Ownership.** Every dataset has an owner, a user or a team ([D4](0004-datasets-as-first-class-objects.md)), holding `dataset.manage` for it: contract, classification, freshness, retention and the projection choices of [D44](0044-minimum-technology-stack.md). Warehouse connections, storage targets and catalogs are tenant resources whose owner sets their policy; the warehouse owner of [D28](0028-warehouse-connection-policy-and-plan-pinning.md) is the connection's owner.
- **Grants to projects.** Amends [D28](0028-warehouse-connection-policy-and-plan-pinning.md) and [D41](0041-ir-text-form-round-trip-and-structure.md). Connections, storage targets, catalogs and agent pools are granted to projects, and a project's environment bindings may map logical names only to resources granted to it, so that editing bindings cannot reach every connection in the tenant. An approval node names who may approve, as users, teams or a project role, checked when the workflow is deployed (MLE 3.4).
- **Clearance.** Amends [D9](0009-cache-scope.md). Each membership carries a clearance, the highest classification whose data content its holder may read; the default is confidential, and restricted is granted only by an admin. Clearance gates data content — previews, samples, downloads, reuse of cached outputs across projects ([D9](0009-cache-scope.md)) and the allowance to project restricted data ([D44](0044-minimum-technology-stack.md)) — and not metadata, which roles govern. A dataset without a classification counts as internal.
- **Run identity.** Triggering a run requires Operator. What a run may read and use is decided by its project's permissions — its own datasets, datasets shared with it ([S20](../documentation/workspace/07-open-items.md)) and the resources granted to it — not by those of whoever triggered it, so that scheduled and production runs do not depend on any one person. The triggering principal is recorded in provenance. Checks are made when the run is planned and recorded in the plan; access revoked during a run applies from the next run, consistent with [D14](0014-input-version-resolution.md).
- **Quality-gate overrides.** Resolves [S18](../documentation/workspace/07-open-items.md). A quarantined version may be released by its dataset's owner or by a Maintainer of its project, configurable per dataset. Every release is audited and does not expire ([D31](0031-execution-state-model.md)).
- **Drafts and commits.** Amends [D41](0041-ir-text-form-round-trip-and-structure.md). Canvas edits are autosaved as drafts held by the platform in its control-plane store, per author and per definition (a workflow or a dataset declaration), recorded against the commit they started from. A draft is not in git and not authoritative; it remains until committed or discarded. The author commits explicitly, with a message, to a branch of their choice, a feature branch by default; one commit may include several changed workflows and dataset declarations, and the three-way merge on the semantic model applies if the branch has moved ([D41](0041-ir-text-form-round-trip-and-structure.md)). Projects without git create a platform-held version (CORE 1.5) at the same explicit step.
- **Version control.** Git holds the history of a git-connected project, and review happens there. The platform holds drafts and, for projects without git, a linear series of versions without branches or reviews; it implements no version control of its own beyond that, and teams that need branching and review connect git.
- **Deploying.** Deployment is an act of the platform, never a side effect of a merge. [D41](0041-ir-text-form-round-trip-and-structure.md)'s publishing of workflows is renamed deploying, leaving publication to datasets ([D15](0015-atomic-publication.md)). Changes reach the branch the platform deploys from by direct commit or pull request, as set per project ([D41](0041-ir-text-form-round-trip-and-structure.md)). The platform pushes with its own credentials on the author's behalf, so it checks roles itself: committing to other branches requires Developer and committing directly to the deploy branch requires Maintainer, while pull requests are reviewed under the git host's protections. Commits record the user as author and the platform as committer, and are audited. The platform watches the deploy branch and deploys each new commit, recording the deployed version by commit hash; a branch ahead of the deployed version is shown as pending deployment.
- **Governed fields.** A dataset's classification, contract and retention require `dataset.manage`; environment bindings and project settings, including the reproducibility setting, require Maintainer. The rule applies to edits in the platform and to commits arriving through git: a commit that changes a governed field deploys only if its git author maps to a principal holding the permission, and otherwise waits until such a principal approves it in the platform. A lowered classification is therefore always an accountable owner's assertion (DE 5.9). How git authors map to principals, for example by verified commit email or a linked account, is settled with the authentication provider.
- **Runs from drafts.** Development and sample runs (CORE 6.6, DS 1.4) may use an uncommitted draft and record a snapshot of its IR and its base commit, so their provenance stays complete ([D7](0007-reproducibility-guarantee.md)). Scheduled and production runs use only deployed definitions.
- **Amends.** [D9](0009-cache-scope.md): clearance is a level held on each membership. [D28](0028-warehouse-connection-policy-and-plan-pinning.md): connections are tenant resources granted to projects. [D30](0030-tenancy-and-isolation-enforcement.md): the mechanism and role model are settled, completing the decision. [D31](0031-execution-state-model.md): quality-gate overrides are assigned. [D41](0041-ir-text-form-round-trip-and-structure.md): drafts and explicit commits replace a commit on every save, workflow publishing is renamed deploying, deployment becomes an act of the platform that checks governed fields, and environment bindings are limited to granted resources. [D42](0042-catalog-persistence.md): unique constraints and foreign keys include the tenant. [D44](0044-minimum-technology-stack.md): allowing restricted data to be projected requires restricted clearance.
- **Quotas and weights.** Amended by [D47](0047-control-plane-structure.md): tenant Admins set project quotas, fair-share weights and per-unit ceilings on pools; a Maintainer may set lower limits within the project, such as per-workflow concurrency.
- **Development runs.** Amended by [D50](0050-development-mode.md): a development run started by a principal reads nothing classified above that principal's clearance; a draft or undeployed commit may raise but never lower governed protection in its runs; development runs use deployed bindings and settings only; Operators may start development runs of commits and deployed versions, Developers also of their own drafts, and CI service accounts within their membership's clearance.

## Rejected alternatives

- Mandatory application scoping alone, under which a single unscoped query leaks across tenants ([D30](0030-tenancy-and-isolation-enforcement.md)).
- Row-level security for project permissions, which would join membership tables for every row.
- An object-relational mapper, which hides the SQL that partitioning, row-level security and batching depend on.
- Runs acting with their triggering user's permissions.
- A commit for every canvas save, or one work-in-progress commit amended on every save.
- Version control of the platform's own in place of git, which would rebuild review, continuous integration and code history that engineers already have.
- The platform as the authority with git as a mirror, under which a refused import leaves git ahead of the platform.
- Accepting changes merged in git under their git author, which would let anyone with merge rights lower a classification or rebind a connection.
