## Context

[D25](0025-processing-engines-and-runtimes.md), [D27](0027-ibis-for-relational-node-definitions.md), [D34](0034-capacity-and-size.md) and [D41](0041-ir-text-form-round-trip-and-structure.md) decided what a node type is responsible for: its runtime, the dialects it supports, its memory behavior, the grouping and order it depends on, its ports, the mode of its output schemas, its value outputs and its version. The detail was left to the IR specification, as was how a fused unit's resource request combines the needs of its segments ([D47](0047-control-plane-structure.md)).

Two principles shape the contract. It declares only what the platform cannot work out for itself: whatever the platform can derive from an implementation, or estimate from data and measurements, it derives or estimates, so that authors write as little as possible and nothing they write can drift from what runs. And a node's parameters are configuration that authors normally fill in as fixed values in a form, yet any of them may need a value known only when a run starts, such as a value of its interval, an item of a map or a value an upstream node computed.

## Decision

What a node type declares, how its parameters are typed and checked, what is derived instead of declared, how code nodes obtain their contract, and how a fused unit's resource request is combined. The normative detail is stated in the IR specification and its schema.

- **Node-type documents.** A node type is described by a document of kind `node_type`, one per version, holding its contract and a reference to its implementation. Node-type documents are not project documents: a project does not commit them, and they live in the platform's catalog of built-in node types and in plugin packages, whose form, naming and distribution are open ([S26]({workspace}/documentation#7.25)). The SDK generates a node type's document from its code, for built-in node types and plugins alike, so that the document is the published, reviewable form of a contract that authors write in code.
- **Identity and versions.** A node type is referenced as `name@version`, the version an integer. A published version is immutable, its image included; any change produces a new version. Workflows pin exact versions and upgrade explicitly ([D41](0041-ir-text-form-round-trip-and-structure.md)). Names form an open namespace: any publisher may define a node type under any name of its own, and names carry no meaning to the platform, which reasons only about contracts. Built-in names are unqualified and reserved ([D56](0056-ir-documents-and-identifiers.md)); names qualified by a publisher are open ([S26]({workspace}/documentation#7.25)).
- **Language and plan.** A node type states the language of its implementation, `python`, `sql` or `command`, and whether its code returns a plan. A node is a plan if and only if its code never receives data. `plan: ibis` marks Python code that receives tables with a schema but no data or connection and returns an Ibis expression over them ([D32](0032-execution-unit-structure.md)); `plan: polars` marks Python code that receives Polars lazy frames over inputs that hold no data and returns a lazy frame built from them; SQL is always a plan, compiled through Ibis. A plan can be fused with its neighbors into one query or lazy plan, and its output schema derived before it runs; an Ibis or SQL plan can also be pushed down to a warehouse and its memory class derived ([D25](0025-processing-engines-and-runtimes.md), [D27](0027-ibis-for-relational-node-definitions.md)). Column lineage does not depend on whether a node is a plan ([D59](0059-column-lineage.md)). Every other node is eager: its code computes its outputs itself and the platform runs it as written; Python code that uses Ibis or Polars to compute data itself is eager, at the cost of those optimizations.
- **Checking plans.** The `plan` field is held to the code, whoever wrote either. A builder receives only inputs that hold no data, so code that needs data fails as it is built; it must return the kind of plan its field names, and the error states what it returned instead; and every leaf of the plan it returns must be one of its inputs or a constant. Since built plans are cached, a builder's result must depend only on its input schemas and parameter values; a value that varies between runs, such as the time of the run, comes in as a parameter. A plan may call functions that run inside the engine, over columns or over batches of rows. They are not a mismatch: each capability they hide degrades on its own, such as lineage, which is task-level for the columns they produce ([D59](0059-column-lineage.md)). A SQL node's query must parse and compile in its dialect. Mismatches are reported when a node is edited and when the SDK generates a node type, never first in a run.
- **Suggestion.** Where eager code returns a lazy plan whose leaves are only its inputs and constants, the platform suggests declaring the node a plan, on the canvas and as a note of the validator; it never changes the node itself.
- **Implementation.** A node-type document names its image, the platform's base image or an image digest, and its entry point: a Python callable for `python`, the query for `sql`, an executable for `command`. A node type whose plan compiles through Ibis lists the warehouse dialects it supports; DuckDB, the engine in process, is always supported. A Polars plan runs on Polars in process and lists no dialects. Every node type lists its execution modes; `batch` is the only mode ([D12](0012-streaming-readiness.md)).
- **Ports.** Inputs and outputs are mappings keyed by name, typed by format type ([D18](0018-format-types-plugin-implementations-and-bindings.md)). An input may be optional or accept several edges, kept in order. Each output port has an output-schema mode, static, derived or dynamic ([D41](0041-ir-text-form-round-trip-and-structure.md)): derived for plan nodes, from their plan, and dynamic for eager nodes unless annotated.
- **Parameters.** Parameters are typed in a profile of JSON Schema 2020-12 restricted to constructs with a counterpart in CEL's types: `string`, `integer`, `number`, `boolean`, `array` and `object` as CEL's `string`, `int`, `double`, `bool`, `list` and `map`, and the formats `date-time` and `duration` as CEL's `timestamp` and `duration`. The platform adds the formats `column` and `column_selector`, selecting columns of a named input port ([D46](0046-control-flow-constructs.md)), `binding`, a logical name bound per environment ([D41](0041-ir-text-form-round-trip-and-structure.md)), and `secret`, a secret reference that expressions never see ([D40](0040-protocol-between-the-control-and-data-planes.md)). Constraints are `enum`, `minimum`, `maximum`, `pattern` and `default`. There is no date type, since CEL has none, and integers and numbers stay distinct, since CEL does not mix them. The same profile types workflow parameters and value outputs.
- **Expressions in parameters.** Any parameter may hold a CEL expression in place of a fixed value ([D41](0041-ir-text-form-round-trip-and-structure.md)), and every value is held to the parameter's type and constraints. The compiler checks an expression's type before any run. A parameter with an `enum` accepts an expression only when the compiler can prove that every value it produces is allowed: a literal, a workflow parameter or value output whose own allowed values are a subset, or a choice between such values; any other expression is rejected. Other constraints are checked when a fixed value is written and, for a computed value, when the control plane evaluates it, before the unit starts, so that a node's code receives only valid values.
- **Value outputs.** A node type declares each value output by name and type.
- **Execution properties.** A node type may name the parameter that supplies its grouping key, by which the planner repartitions ([D25](0025-processing-engines-and-runtimes.md)), and the parameter that supplies its sort key, required when its result depends on order ([D27](0027-ibis-for-relational-node-definitions.md)). It may name the parameter that seeds its randomness, so that the seed is always a resolved and recorded parameter; tiers otherwise follow [D7](0007-reproducibility-guarantee.md), under which only verification establishes Reproducible. A node with an external side effect names the binding parameter of its target: such a node is never served from cache ([CORE 2.12]({workspace}/documentation#3)) or fused ([D33](0033-automatic-fusion.md)), checks its lease and uses idempotency keys ([D40](0040-protocol-between-the-control-and-data-planes.md)), and in a development run executes only if the run's environment binds that target itself ([D50](0050-development-mode.md)).
- **Memory behavior.** A node's memory class ([D34](0034-capacity-and-size.md)) is an input to the planner's estimate rather than a field authors must fill in. It is derived from the compiled query of an Ibis or SQL plan, from the operators DuckDB spills and those it does not ([D27](0027-ibis-for-relational-node-definitions.md)); it defaults to blocking and non-spilling for every other node, the conservative case; and it is refined from measured peaks ([D34](0034-capacity-and-size.md), [D47](0047-control-plane-structure.md)). A node type may declare it as a hint where it knows better.
- **Resources.** A node type declares no resource quantities beyond what estimation cannot infer: whether it needs a GPU, can use one, or neither (`required`, `supported` or `none`, the default), and optionally a memory floor for overhead independent of its data. Units are sized from estimates ([D34](0034-capacity-and-size.md), [D47](0047-control-plane-structure.md)); a node may set its own resources in the workflow, and whether a node that supports a GPU receives one is set there.
- **Placement.** A node type states what its implementation can run on, never where it runs: the planner chooses by data location and capacity ([D25](0025-processing-engines-and-runtimes.md), [D34](0034-capacity-and-size.md)). A plan node is eligible for every engine its plan compiles to: an Ibis or SQL plan for DuckDB and the warehouse dialects it supports, a Polars plan for Polars in process. A workflow may override the planner's choice for a node among the engines the node is eligible for, the same for every node. Hard constraints ([D26](0026-placement-constraints.md)) and eligibility come before the override: an override naming an engine the node is not eligible for, or one the hard constraints exclude, is an error before the run. The plan records the chosen engine with its reason, an override included, and pins it like any placement ([D28](0028-warehouse-connection-policy-and-plan-pinning.md)).
- **Code nodes.** A code node runs a file under `code/` written in one of the languages, following an interface of that language: for Python, the plan interfaces of Ibis and Polars or an eager interface. The languages form an open set, each added with its interfaces and a static reader. The compiler derives the node's contract from the file by static analysis of its signature and annotations, without executing it ([D21](0021-architecture-planes.md)), so the workflow holds only the node's wiring and parameter values and nothing can drift from the code. A `command` code node's declaration in the workflow is its interface, since a command has no signature to read.
- **One path for every node.** Built-in node types, plugins and code nodes are compiled, planned and run in the same way: a built-in node type is a node type the platform publishes, with no path of its own.
- **Derivation in the data plane.** A plan's builder runs only in derivation units in the data plane, which receive schemas and parameter values but no data, credentials or network. Derivation returns the plan's output schemas and its compiled plan: the query in the dialect of the engine chosen for it, or the serialized lazy plan, compiled for each fused segment as a whole. Execution units run the compiled plan and never call the builder, so plan code never meets data; functions inside a plan run in the execution unit, as the code of any node does. Results are cached per tenant by node-type version and image, input schemas, parameter values and, for compiled plans, the dialect; session units ([D50](0050-development-mode.md)) keep derivation warm. The pool that runs derivation units is chosen by the same rule as the pool for probes, which is still open ([D49](0049-source-probes.md)). Where no data plane is reachable, a deployment that needs a new derivation waits, naming the pool it waits for, and is never made without it. The control plane never runs a node's code, the platform's own included ([D21](0021-architecture-planes.md)).
- **Fused units.** Data handed between the segments of a unit is taken to be held whole in memory. A unit's memory, CPU and ephemeral disk are each the maximum, over its segments, of the larger of its nodes' floors and the segment's estimate, which for memory includes the data handed to and from it. Nodes are fused only when the GPUs they request are equal, which is what compatible resources means in [D33](0033-automatic-fusion.md)'s legality rule, and the unit requests that GPU. A unit's deadline is the sum of its nodes' timeouts, a node contributing the timeout its workflow sets or, without one, the platform's default.
- **Amends.** [D25](0025-processing-engines-and-runtimes.md): the runtime is the language of a node's code and whether that code returns a plan; plan nodes are chained into segments; an override of the engine follows hard constraints and eligibility and is shown with its reason, for every node. [D27](0027-ibis-for-relational-node-definitions.md) and [D34](0034-capacity-and-size.md): the memory class is derived or defaulted, and declared only as a hint; Ibis compiles in derivation units; the override follows hard constraints and eligibility once an engine at the same location is added. [D32](0032-execution-unit-structure.md): a Polars lazy plan is built by plan nodes, and units run compiled plans. [D33](0033-automatic-fusion.md): compatible resources are equal GPU requests. [D41](0041-ir-text-form-round-trip-and-structure.md): each output port has its own schema mode, and code nodes obtain their contract from their code. [D47](0047-control-plane-structure.md): the request of a fused unit is combined as above; the compiler obtains the derived output schemas of plan nodes from the data plane; and the override follows hard constraints and eligibility. [D56](0056-ir-documents-and-identifiers.md): node-type documents are a kind beside the project documents.

## Consequences

- The palette, the canvas's forms and plugin registration all read node-type documents, and code nodes reuse their definitions.
- The compiler needs a static reader for each language of code nodes.
- Schemas shown while editing on the canvas need a round trip to the data plane, which caching keeps short.
- Planning estimates are conservative for opaque code until measurements refine them.
- A plan is built once for each cache key. Compiling it for the engine the planner chose needs the data plane before its unit is dispatched, and a parameter whose value is computed when the run starts can miss the cache.
- A serialized Polars plan is read only by the Polars version that wrote it, and functions inside it travel with it in serialized form; both hold because derivation and execution use the node type's own image.

## Rejected alternatives

- A contract stated only in the specification, with node types defined in code alone. Plugins, the canvas and the plugin registry would have no file to register, render and review.
- Parameters typed by JSON Schema without restriction. Constructs such as `oneOf` and conditional schemas have no counterpart in CEL's types, so expressions over such parameters could not be type-checked before a run.
- A type vocabulary of the platform's own. It would add a format that authors and tools must learn, where a restricted profile of JSON Schema serves equally and matches the schema of the documents.
- Parameters accepting only fixed values. Values that depend on the run's interval, on the item of a map or on an upstream result would each need a mechanism of their own.
- Node types marking the parameters that may hold expressions. With every value held to its type and constraints, the restriction protects nothing, and it would stop authors varying per run what a node type's author did not foresee.
- Parameters holding only fixed values or plain references, with every computation in a node of its own. Each small derivation, such as a lookback window or a path per day, would need a node.
- A declared determinism. The platform cannot check it, and [D7](0007-reproducibility-guarantee.md) already reaches Reproducible only through verification.
- Resource quantities fixed by the node type. Needs depend on the data a unit processes, which the planner estimates.
- A memory class every node type must declare. It can be derived for Ibis and SQL plans and defaulted safely for the others.
- A GPU field stating only a requirement. Many implementations run on a CPU and can use a GPU.
- Contracts of code nodes written by hand in the workflow. They would duplicate the code and drift from it.
- Contracts of code nodes obtained by importing the code. The control plane never runs user code, and importing it in the data plane would cost a round trip on every edit.
- Node types naming an engine or cluster. The planner chooses where work runs.
- An override that precedes hard constraints. It would let an author move restricted data out of its warehouse or past residency rules.
- A single runtime field naming a language or a library. It mixed what interprets the code with whether the code returns a plan.
- Treating all Polars code as eager. Polars code that builds a lazy plan over inputs holding no data is checked as an Ibis plan is, and gains fusion and derived schemas, which the platform derives wherever it can.
- Calling builders again in the execution unit and checking the plan they return. Plan code would then meet data, and a builder that collects data whenever it can would have to be caught in every run.
- Building each plan twice and comparing the results. It would double the time of every derivation, on every edit, to catch only part of what the rule on a builder's result forbids.
- Forbidding functions that run inside a plan. Each capability they hide degrades on its own; forbidding them would push such code into eager nodes and lose the rest.
- Converting eager code into plans automatically. A plan may run on another engine, which changes results, cache keys and pinned plans, and eager code is called differently from a builder.
- Deriving the schemas of built-in node types in the control plane. It would give built-ins a path of their own and break the rule that the control plane never runs node code.
- Assuming data streams between a unit's segments. Unconfirmed, it would understate memory needs.

## Follow-ups

- The interfaces code files follow in each language, with the SDK (design agenda).
- How a `command` node type turns its ports and parameters into a command line and files, with the palette (design agenda).
- How a static output port declares its columns, with the schemas of dataset declarations.
- Relaxing the assumption that data handed between segments is held whole in memory, once it is measured.
- Where compiling plans for the engines the planner chose sits in the course of a run ([D47](0047-control-plane-structure.md)).
- For the check of a plan's leaves: telling the platform's own input sources apart from sources a builder registers itself, and reading the leaves of Ibis plans.
- Deriving the memory class of Polars plans.
- Which dialects a SQL node is eligible for, from the dialect its query is written in and those it can be transpiled to.
- The syntax of engine overrides, and whether a workflow or project may set a default engine for its nodes, with the workflow documents (design agenda).
