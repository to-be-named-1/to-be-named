## Context

**Git authoritative, YAML canonical** (D41). Python as the round-trip format was rejected because free-form code cannot be regenerated from a canvas edit without destroying the author's code; a one-way Python SDK keeps that practice available. Hashing the normalized semantic model rather than the text keeps comments, formatting and migrations from invalidating caches.

**A restricted expression language** (D41). User-written conditions are evaluated by the control plane, which never runs user code ([D21](0021-architecture-planes.md)). Python or Jinja there would let a condition reach files, the network or other tenants, or never terminate; running each condition in a container instead would cost a start-up per decision and hide the plan until run time. CEL always terminates, has no side effects and is typed, so it is safe to evaluate and checkable before a run; logic beyond it runs in a Python code node that emits typed values.

## Decision

The text form of the IR, how it round-trips between canvas and git, how it is hashed and versioned, how a project's repository is laid out, port types, and the expression language used for control flow and parameters.

- **Text syntax.** The canonical text form is a strict subset of YAML, without anchors, aliases or custom tags, which do not survive a structured write-back. Its data model is JSON's, and unquoted values are typed by the IR specification rather than by the parser ([D56](0056-ir-documents-and-identifiers.md)). A Python SDK that generates IR in one direction follows the first slice; a document marked as generated, by it or by any other tool, appears read-only on the canvas ([D58](0058-behavior-follows-properties.md)), so teams that author pipelines in Python keep that practice ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)) without breaking round-tripping.
- **Authority.** For a project connected to git, git is authoritative. Canvas saves are commits on a draft branch; publishing to the branch the platform deploys from is a direct commit or a pull request, set per project. Projects without git use versions held by the platform ([CORE 1.5]({workspace}/documentation#3)). An edit made on an older base is merged three ways on the semantic model, not the text, and real conflicts are shown to the author as a diff to resolve. Amended by [D45](0045-isolation-enforcement-and-role-model.md): canvas edits are autosaved as drafts held by the platform and committed only when their author chooses, with a message; deployment from the branch the platform deploys from is an act of the platform, which holds back commits that change governed settings until an authorized person approves them; workflow publishing is called deploying, keeping publication for datasets.
- **Merge-friendly files.** One workflow per file, deterministic key order, and stable node keys separate from display titles, generated by writers where an author does not write them, and changed after deployment only by an explicit refactor ([D56](0056-ir-documents-and-identifiers.md)). Amended by [D44](0044-minimum-technology-stack.md): the parser is goccy/go-yaml; comments are not preserved on write-back in the first slice, the canvas warns before a save would remove them, and commentable collections are keyed by stable identifier so that preservation can be added later.
- **Hashing.** Cache keys are computed over a normalized semantic model, never the text, so comments, ordering and formatting never change a key. A separate key-schema version ensures that an IR migration which does not change meaning leaves keys unchanged; a change to how keys are computed causes at most a one-time wave of misses ([D8](0008-cache-keying.md)).
- **Non-semantic layer.** Canvas layout is a sidecar file committed beside each workflow, keyed by node identifier, with rounded coordinates and deterministic order, and never affects keys; where it is missing the canvas lays the workflow out automatically. Inline composites belong to this layer, not to the IR. A referenced workflow is a `uses` node pinned to a version ([D31](0031-execution-state-model.md)); the canvas offers upgrades but never follows the latest version.
- **Environment bindings.** Definitions refer only to logical names for connections, storage targets, secret references ([D40](0040-protocol-between-the-control-and-data-planes.md)) and agent-pool overrides; a bindings file per environment maps them to concrete values ([MLE 6.2]({workspace}/documentation#6)). A change of binding affects cache keys only through the resolved identity of inputs and source versions, never through the logical name. Amended by [D45](0045-isolation-enforcement-and-role-model.md): bindings may name only resources granted to the project.
- **Repository layout.** `project.yaml` holds project configuration, including the reproducibility setting ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)); `workflows/<name>.yaml` holds one workflow with its schedule and logical interval ([D13](0013-partitioning-intervals-and-dataset-ownership.md)), beside its layout sidecar; `datasets/<path>.yaml` declares a dataset — schema or contract, partitioning, classification, retention and freshness, and for a source its storage choice ([D35](0035-ephemeral-extraction.md)) and change-detection strategy ([D37](0037-incremental-extraction-state.md)); `code/` holds code-node files referenced by path, from which the compiler derives the nodes' contracts ([D57](0057-node-type-contract.md)) and whose content hash is part of the node's semantic fields, so code is reviewed, linted and tested as ordinary files ([MLE 6.1]({workspace}/documentation#6)); `environments/<env>.yaml` holds bindings.
- **Output schemas.** Each output port has one of three modes, derived for plan nodes ([D57](0057-node-type-contract.md)): **static**; **derived**, computed at authoring time from input schemas and parameters — for Ibis nodes from the expression's own schema; or **dynamic**, depending on the data, such as a pivot over discovered values. A dynamic node may declare expected columns; otherwise its downstream schema is shown as pending until a sample run ([DS 1.4]({workspace}/documentation#5)), and the last observed schema is kept for authoring. Enforced contracts are checked at publication; authoring never refuses a graph because a schema is pending ([D36](0036-data-engineering-practice-first-reproducibility-by-choice.md)). Column lineage through dynamic columns is resolved after the run. This resolves [S24]({workspace}/documentation#7.24).
- **Versioning.** Three axes are kept apart: the IR version ([D56](0056-ir-documents-and-identifiers.md)), migrated on read with a window of older versions supported, and written back only by an explicit commit, never by silently rewriting the repository; node-type versions, written `type@version` and upgraded explicitly, with a bulk upgrade that shows its effect; and the unit specification ([D40](0040-protocol-between-the-control-and-data-planes.md)), which shields agents from both.
- **Port types.** A port type is a format type ([D18](0018-format-types-plugin-implementations-and-bindings.md)), such as `tabular` or `genomics/bam@1`; for tabular data an optional schema in Arrow logical types, since the engines exchange Arrow; and an open map of namespaced annotations, preserved even when not recognized, which leaves room for split roles ([DS 2.8]({workspace}/documentation#5)) without a schema change. Compatibility between connected ports is checked at authoring time ([CORE 1.2]({workspace}/documentation#3)).
- **Expression language.** Conditions, map collections, loop termination, parameter interpolation and derived values written by users are expressions in CEL (Common Expression Language), evaluated by the control plane. CEL is not Turing-complete: an expression always terminates at a cost bounded by its size and inputs, has no side effects and cannot reach files, the network or other tenants, so the control plane can evaluate it without running user code ([D21](0021-architecture-planes.md)). It is typed, so the validator knows every reference and the result type before a run ([D2](0002-graph-model.md), [CORE 1.2]({workspace}/documentation#3)). Arbitrary code such as Python or Jinja templates was rejected for these positions: evaluated in the control plane it would break [D21](0021-architecture-planes.md), and evaluated in the data plane every decision would cost a container start and the plan could not be known in advance. Amended by [D44](0044-minimum-technology-stack.md): the control plane evaluates expressions with cel-go, with a cost limit on every program; how the canvas checks expressions is settled with the visual builder.
- **Syntax.** One delimiter, `${{ … }}`. A value consisting of a single expression keeps its type, so `${{ params.regions }}` is a list; an expression embedded in a string is formatted as text.
- **Scope.** Expressions may reference `params`, typed by the workflow's parameter schema; `interval`, its start, end and timezone ([D13](0013-partitioning-intervals-and-dataset-ownership.md)); declared value outputs of upstream nodes, `outputs.<node>.<value>`; and `run` metadata, in operational fields only. They never reference secrets, which remain a separate typed field ([D40](0040-protocol-between-the-control-and-data-planes.md)). The function library covers dates and times on the interval, strings and lists, and has no wall clock and no randomness, so resolved values are deterministic ([D7](0007-reproducibility-guarantee.md), [D8](0008-cache-keying.md), [D14](0014-input-version-resolution.md)). Amended by [D46](0046-control-flow-constructs.md): inside a loop, expressions may also reference `loop.index`, `loop.carried.<name>` and the current iteration's value outputs.
- **Value outputs.** A node type may declare value outputs: small typed values such as a row count, a metric or a list of keys or paths. They travel to the control plane as state-bearing messages, filtered by classification in the agent ([D40](0040-protocol-between-the-control-and-data-planes.md)); bulk data never feeds an expression, and work over large collections uses partitions and fan-out ([CORE 2.3]({workspace}/documentation#3), [D13](0013-partitioning-intervals-and-dataset-ownership.md)).
- **Escape hatch.** Logic too complex for an expression is written in a Python code node, which runs in the data plane and emits typed value outputs that expressions then read.
- **Run conditions on upstream outcomes.** Each node has a run rule over the outcomes of its upstream nodes ([D31](0031-execution-state-model.md)): all succeeded, the default; all finished whatever their outcome; any failed; and similar. A rule may be combined with a CEL condition, which supports clean-up, alerting and fallback branches. Amends [D2](0002-graph-model.md).
- **Canvas.** An `if` is a branching node with labeled then and else edges; a map and a loop are frames enclosing their body, with the collection or termination rule in the frame header. Conditions are built with a rule builder that generates the expression, with an expression mode offering autocomplete and inline type errors; any parameter field may switch between a fixed value and an expression. Amended by [D46](0046-control-flow-constructs.md): an n-way switch and merge nodes for alternative branches are added, and loop frames declare their carried state and execution mode.
- **Development bindings.** Amended by [D50](0050-development-mode.md): a development run uses the bindings of a non-production environment, the development environment by default. For logical names it does not define, reads fall back to the production environment's bindings; side effects never fall back. Bindings take effect only from deployed definitions.
